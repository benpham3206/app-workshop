# Customer and creator stack

> Corrections from [`06_factcheck.md`](06_factcheck.md) are applied inline and marked **[FC]**.

## Decision

**[INFERENCE] Recommended default for the factory:** use RevenueCat for purchase processing and entitlement state, but keep Apple purchases as the default storefront. Give customers a restore path, a working subscription-management route, refund guidance, support contact, and—if the app has accounts—an in-app account-deletion flow. For creators, start with read-only RevenueCat and App Store Connect access from the creator’s Mac, plus Apple’s built-in operational reports. Add third-party analytics, crash reporting, chat, and web billing only when the product has a specific need for them.

**[INFERENCE] Platform boundary:** RevenueCat’s purchase SDK supports the Apple platforms in scope, but its hosted Paywalls UI is documented for iOS/iPadOS, Mac Catalyst, and macOS—not watchOS or visionOS. Customer Center is documented for iOS and Android, with cancellation and some management options only; macOS Customer Center is explicitly unsupported. Treat watchOS and visionOS as companion surfaces that route purchase management to a supported app or Apple’s system UI, not as places where all RevenueCat UI is available.

**[FACT — RevenueCat GitHub Releases, checked 2026-10-19]** The latest `purchases-ios` release is **5.96.0** (2026-10-16) **[FC]**. The package URL RevenueCat recommends for Swift Package Manager is `https://github.com/RevenueCat/purchases-ios-spm.git`. [Release list](https://github.com/RevenueCat/purchases-ios/releases), [installation guide](https://www.revenuecat.com/docs/getting-started/installation/ios).

## 1. RevenueCat: customer purchases and support

### Native app wiring

- **[FACT — RevenueCat Quickstart, checked 2026-10-19]** Add `RevenueCat` to purchase-enabled targets and call `Purchases.configure(withAPIKey:)` once during app startup, using that app’s **public SDK key**. Identify a customer with a stable, non-sensitive App User ID only if the app has its own account identity; otherwise RevenueCat can use an anonymous ID. [Quickstart](https://www.revenuecat.com/docs/getting-started/quickstart), [installation](https://www.revenuecat.com/docs/getting-started/installation/ios).
- **[FACT — RevenueCat Quickstart, checked 2026-10-19]** Gate paid functionality from `CustomerInfo.entitlements[<entitlement-id>]?.isActive`, rather than hard-coding product IDs throughout the app. Fetch `CustomerInfo` after purchase, restore, and when refreshing access; keep entitlement checks explicit and recoverable when network access fails. [Quickstart](https://www.revenuecat.com/docs/getting-started/quickstart).
- **[FACT — RevenueCat Paywalls docs, checked 2026-10-19]** Fetch `Purchases.shared.offerings()` to get the current `Offering` and its `Package`s. Offerings map products to a purchase presentation; entitlements represent the access the purchase grants. The offering’s metadata is also available in the SDK for remote presentation/config values. [Offerings and paywalls](https://www.revenuecat.com/docs/tools/paywalls), [offering metadata](https://www.revenuecat.com/docs/tools/offering-metadata).
- **[FACT — RevenueCat Paywalls docs, checked 2026-10-19]** `RevenueCatUI.PaywallView` embeds a paywall in a SwiftUI view. `.presentPaywallIfNeeded(requiredEntitlementIdentifier:)` presents one when the customer lacks the named entitlement. RevenueCat says its iPad `presentPaywallIfNeeded` presentation is roughly iPhone-sized; use `PaywallView` directly if the iPad layout should fill the available space. [Displaying Paywalls](https://www.revenuecat.com/docs/tools/paywalls/displaying-paywalls).
- **[FACT — RevenueCat platform notes, checked 2026-10-19]** Paywalls support iOS 15+, Mac Catalyst 15+, and native macOS 12+. RevenueCat’s platform list explicitly excludes watchOS, tvOS, and visionOS Paywalls UI. Native macOS Paywalls require `purchases-ios` 5.39.0+ and use editor-built paywalls; legacy templates are unsupported there. [Paywalls](https://www.revenuecat.com/docs/tools/paywalls), [displaying Paywalls](https://www.revenuecat.com/docs/tools/paywalls/displaying-paywalls).
- **[INFERENCE]** Put purchase and entitlement code in iPhone/iPad and Mac targets. On Watch, expose a companion status or link to manage the plan from the iPhone. For visionOS, verify current SDK/UI availability before promising a paywall.

### Customer Center: manage, cancel, refund, restore

- **[FACT — RevenueCat Customer Center docs, checked 2026-10-19]** Present `CustomerCenterView()` from RevenueCatUI, usually as a settings/account sheet. Its default paths include cancellation and missing purchases; refund requests and plan changes are marked **iOS only**. Users without an active subscription generally get a restore option. [iOS integration](https://www.revenuecat.com/docs/tools/customer-center/customer-center-integration-ios), [configuration](https://www.revenuecat.com/docs/tools/customer-center/customer-center-configuration).
- **[FACT — RevenueCat docs, checked 2026-10-19]** The Customer Center can display retention promotional offers for cancellation and refund flows, but the offers must first be created in App Store Connect and their identifiers configured in RevenueCat. [Customer Center configuration](https://www.revenuecat.com/docs/tools/customer-center/customer-center-configuration).
- **[FACT — RevenueCat docs, checked 2026-10-19]** Customer Center has callbacks for restore initiation/completion, showing subscription management, refund-request start/completion, feedback surveys, management-option selections, and custom actions. Use the callbacks for app state and support instrumentation; don’t treat “refund request completed” as proof Apple granted a refund. [iOS integration](https://www.revenuecat.com/docs/tools/customer-center/customer-center-integration-ios).
- **[FACT — RevenueCat docs, checked 2026-10-19]** Customer Center is not available on native macOS; it is supported on Mac Catalyst 15+ **[FC]**. The documented default and capabilities are iOS/Android, so do not promise equivalent hosted management UI on Mac, Watch, or Vision Pro without a new platform check. [Customer Center configuration](https://www.revenuecat.com/docs/tools/customer-center/customer-center-configuration), [macOS Paywall notes](https://www.revenuecat.com/docs/tools/paywalls/displaying-paywalls).
- **[INFERENCE]** For targets without Customer Center, provide a clear “Manage subscription” route using Apple’s subscription-management UI and a separate “Request a refund” route to Apple. Keep restore available through RevenueCat’s restore API (`restorePurchases`) or Customer Center where supported. Don’t expose a backend refund action as a substitute for Apple’s refund process.
- **[FACT — Apple App Store Server API docs, checked 2026-10-19]** Apple provides refund-history access and a `Send Consumption Information` endpoint for a server responding to a `CONSUMPTION_REQUEST` notification. These APIs support a developer backend’s refund workflow; they are not a general-purpose customer refund button. [App Store Server API](https://developer.apple.com/documentation/appstoreserverapi).

### Web billing, Paywalls v2, experiments, charts, and customer lists

- **[FACT — RevenueCat Web docs, checked 2026-10-19]** Web Purchase Links are hosted purchase flows. RevenueCat Web supports RevenueCat Billing, Stripe Billing, or Paddle Billing; the selected billing engine controls different parts of product setup, checkout, taxes, emails, and subscription management. Web purchases can share RevenueCat entitlements with mobile apps. [Web Purchase Links](https://www.revenuecat.com/docs/web/web-billing/web-purchase-links), [RevenueCat Web overview](https://www.revenuecat.com/docs/web/payment-integrations).
- **[FACT — RevenueCat Web docs, checked 2026-10-19]** An identified Web Purchase Link needs the App User ID attached; Redemption Links support anonymous web purchases that can later be associated with an app user. Web paywalls do not show a mobile restore-purchases link. [Web Purchase Links](https://www.revenuecat.com/docs/web/web-billing/web-purchase-links), [Web Paywalls](https://www.revenuecat.com/docs/web/paywalls).
- **[FACT — RevenueCat, checked 2026-10-19]** RevenueCat says web functionality is included in RevenueCat pricing, but that is not the same as saying payment processing, taxes, or the selected Stripe/Paddle service have no cost. [RevenueCat Web overview](https://www.revenuecat.com/docs/web/web-billing/overview), [pricing](https://www.revenuecat.com/pricing/).
- **[FACT — Apple/RevenueCat external purchase docs, checked 2026-10-19]** RevenueCat Web does not itself establish that in-app links to web checkout are permitted in every storefront. Apple’s regional entitlements, disclosures, and terms apply. RevenueCat’s in-app web-checkout flow is described as private beta in its docs. Verify rules and entitlements for each storefront before enabling it. [RevenueCat app-to-web purchases](https://www.revenuecat.com/docs/tools/paywalls/creating-paywalls/web-purchase-button).
- **[FACT — RevenueCat Paywalls docs, checked 2026-10-19]** Paywalls v2 are remotely configurable, editor-built paywalls rendered with native UI. RevenueCat’s current docs require `purchases-ios` 5.27.1+ for Paywalls generally and 5.83.0+ for multi-step paywalls; the latest 5.96.0 release is above those stated minimums **[FC]**. [Paywalls](https://www.revenuecat.com/docs/tools/paywalls), [releases](https://github.com/RevenueCat/purchases-ios/releases).
- **[FACT — RevenueCat Experiments docs, checked 2026-10-19]** Experiments can compare pricing, offers, product mixes, paywall design, and retention messages. The docs list Experiments for Pro and Enterprise; current pricing advertises A/B/n growth tools and the Pro plan’s features. Confirm the actual account plan and eligibility in the dashboard before making Experiments a required factory feature. [Experiments](https://www.revenuecat.com/docs/tools/experiments-v1), [pricing](https://www.revenuecat.com/pricing/).
- **[FACT — RevenueCat Charts docs, checked 2026-10-19]** RevenueCat Charts v3 is the default charts experience; most charts update in real time and are based on purchase data stored by RevenueCat, independent of app-side event logging. [Charts](https://www.revenuecat.com/docs/dashboard-and-metrics/charts).
- **[FACT — RevenueCat customer docs, checked 2026-10-19]** The former Customer Lists are now called **Audiences**. RevenueCat’s dashboard customer search can find users by App User ID, transaction ID, email attribute, or Apple order ID (the latter requires purchase-key setup and production purchase). [Audiences / legacy Customer Lists](https://www.revenuecat.com/docs/dashboard-and-metrics/customer-lists).

## 2. RevenueCat creator console API

### Readable data and routes

**[FACT — RevenueCat REST API v2 docs, checked 2026-10-19]** REST API v2 is `https://api.revenuecat.com/v2`; it uses `Authorization: Bearer <key>`. The docs say to create **new v2 secret keys** with explicit endpoint permissions; v1 keys do not work with v2. Use only the smallest read scopes needed for a dashboard. [API v2 overview](https://www.revenuecat.com/docs/api-v2).

A read-only creator console can use these endpoint families:

- **[FACT — RevenueCat API v2, checked 2026-10-19] Metrics:** `GET /v2/projects/{project_id}/metrics/overview`, `GET .../metrics/revenue`, and `GET .../charts/{chart_name}` (plus `/options`). These provide RevenueCat’s supported overview and subscription charts. [Charts & Metrics API](https://www.revenuecat.com/docs/api-v2/charts-and-metrics).
- **[FACT — RevenueCat API v2, checked 2026-10-19] Customers:** `GET /v2/projects/{project_id}/customers` supports search; `GET .../customers/{customer_id}` reads a customer profile. Customer attributes, aliases, subscriptions, purchases, and events have related customer-resource routes. The read permission is `customer_information:customers:read`. [Customer API](https://www.revenuecat.com/docs/api-v2/customer).
- **[FACT — RevenueCat API v2, checked 2026-10-19] Subscriptions:** `GET /v2/projects/{project_id}/subscriptions` searches by store subscription identifier; `GET .../subscriptions/{subscription_id}` reads one; customer-specific subscription data can also be read from the customer resource routes. [Subscription API](https://www.revenuecat.com/docs/api-v2/subscription).
- **[FACT — RevenueCat API v2, checked 2026-10-19] Transactions:** `GET /v2/projects/{project_id}/subscriptions/{subscription_id}/transactions` returns transaction history with purchase date, product, and gross/commission/tax/proceeds values. It requires `customer_information:subscriptions:read`. [Subscription Transactions](https://www.revenuecat.com/docs/api-v2/subscription-transactions).
- **[FACT — RevenueCat API v2, checked 2026-10-19] Other useful operations:** RevenueCat exposes customer grant/revoke, transfer, offering overrides, web subscription management, refunds for some web stores, and deletion endpoints. These are **write** operations. The creator console should hide them or require a deliberate human confirmation with an audit trail; they are not required for reporting. [Customer API](https://www.revenuecat.com/docs/api-v2/customer), [Subscription API](https://www.revenuecat.com/docs/api-v2/subscription).
- **[INFERENCE]** For an operator who runs the factory for clients, use a separate RevenueCat v2 key per client/project with read scopes, and store it in that client’s local credential record. Avoid one broad key that spans unrelated projects.

### Webhooks and rate limits

- **[FACT — RevenueCat, checked 2026-10-19]** Webhooks deliver purchase/subscription event POSTs. Configure an authorization header and enable HMAC signing; verify `X-RevenueCat-Webhook-Signature` against the raw request body, use constant-time comparison, and make event handling idempotent. RevenueCat retries failed deliveries up to five times, then stops. [Webhooks](https://www.revenuecat.com/docs/integrations/webhooks).
- **[FACT — RevenueCat API v2, checked 2026-10-19]** Documented v2 default rate limits are 480 requests/minute for Customer Information, 25/minute for Charts & Metrics, and 60/minute for Project Configuration. Limits are shared by domain and apply per app-level key or per developer for developer-level keys. Successful responses provide current-use/current-limit headers; `429` responses include `Retry-After`. [API v2 rate limits](https://www.revenuecat.com/docs/api-v2).
- **[UNKNOWN]** RevenueCat’s docs describe scoped secret keys and key types, but I did not verify a formal “project-level v2 key” label as distinct from the UI’s project-scoped key creation. The docs’ workflow is to create a v2 secret key in Project Settings and select its permissions. [API v2 overview](https://www.revenuecat.com/docs/api-v2).

## 3. App Store Connect creator console

### What can be read programmatically

- **[FACT — Apple App Store Connect API, checked 2026-10-19]** The API can list apps (`GET /v1/apps`) and related metadata, versions, builds, TestFlight resources, in-app purchases, reviews, reports, and performance metrics. It uses JWTs signed with an App Store Connect API private key. Apple warns that API changes affect production App Store Connect data, so keep a reporting console read-only by default. [API overview](https://developer.apple.com/documentation/appstoreconnectapi), [List apps](https://developer.apple.com/documentation/appstoreconnectapi/get-v1-apps).
- **[FACT — Apple, checked 2026-10-19] Builds/TestFlight:** the API includes prerelease versions, builds, beta groups, beta testers, and related TestFlight resources. It can also manage beta testers and groups and submit builds for TestFlight App Review. [TestFlight API overview](https://developer.apple.com/documentation/appstoreconnectapi).
- **[FACT — Apple, checked 2026-10-19] Store versions and releases:** the API can create app versions, manage App Store metadata, submit versions for review, and release approved apps. These are write operations; read status in the creator console, but gate submission/release actions behind explicit human intent. [App Store Connect API](https://developer.apple.com/documentation/appstoreconnectapi).
- **[FACT — Apple, checked 2026-10-19] Reviews:** `GET /v1/apps/{id}/customerReviews` reads reviews, with territory/rating filters. The Customer Review Responses resources create/update, read, and delete a public response. [Customer Reviews](https://developer.apple.com/documentation/appstoreconnectapi/customer-reviews), [responses](https://developer.apple.com/documentation/appstoreconnectapi/customer-review-responses).
- **[FACT — Apple, checked 2026-10-19] Sales and finance:** the API can download Sales and Trends and finance reports. Apple says these endpoints require a **Team key** and cannot be used with an Individual key. [Sales and Finance](https://developer.apple.com/documentation/appstoreconnectapi/sales-and-finance).
- **[FACT — Apple, checked 2026-10-19] Analytics reports:** report categories include store engagement, commerce, app usage, framework usage, and performance. Reports are compressed tab-delimited files; recurring reports may take approximately 24–48 hours for the first report, and daily data is considered complete two days after the report date. Data is privacy-thresholded and may be missing for low-volume activity. [Analytics Reports API](https://developer.apple.com/documentation/appstoreconnectapi/downloading-analytics-reports), [overview](https://developer.apple.com/help/app-store-connect-analytics/overview/analytics-reports-api/).
- **[FACT — Apple, checked 2026-10-19] perfPowerMetrics:** the read-only `perfPowerMetrics` resource provides aggregate App Store-version and build metrics, diagnostic signatures, and downloadable anonymized logs. Availability depends on customers opting in to share diagnostics and enough report data being present. [Power and Performance Metrics and Logs](https://developer.apple.com/documentation/appstoreconnectapi/power-and-performance-metrics-and-logs).
- **[FACT — Apple, checked 2026-10-19] Xcode Cloud:** the API reads products, workflows, builds, artifacts, issues, test results, repositories, and pull requests; it can start builds and create/update/delete workflows. Deleting a workflow also deletes its associated build information and artifacts. [Xcode Cloud workflows and builds](https://developer.apple.com/documentation/appstoreconnectapi/xcode-cloud-workflows-and-builds), [workflows](https://developer.apple.com/documentation/appstoreconnectapi/workflows).
- **[INFERENCE]** This is enough for a useful creator dashboard: release/build status, reviews and replies, sales/subscription reports, crash/performance trends, and CI status. It is not a general feed of identifiable customer behavior or private customer identities. Apple’s analytics reports are aggregated and thresholded.

### Keys and roles

- **[FACT — Apple, checked 2026-10-19] Team keys** are created by an Account Holder or Admin, can be assigned roles, and apply across all apps in the account; the team key cannot be limited to one app. Sales/Finance specifically requires a Team key. [Creating API Keys](https://developer.apple.com/documentation/appstoreconnectapi/creating-api-keys-for-app-store-connect-api), [API setup](https://developer.apple.com/help/app-store-connect/get-started/app-store-connect-api/).
- **[FACT — Apple, checked 2026-10-19] Individual keys** inherit the associated user’s roles and app access, but cannot access Provisioning endpoints, Sales and Finance, or `notaryTool`. Apple notes that they can only be downloaded once. [Creating API Keys](https://developer.apple.com/documentation/appstoreconnectapi/creating-api-keys-for-app-store-connect-api).
- **[INFERENCE]** For a read-only client console, prefer a least-privilege individual key where its permissions cover the needed reports. If finance reports are required, a Team key is necessary and its all-app scope is a meaningful risk; create a separate low-privilege team key only if the account owner accepts that scope.
- **[FACT — Apple, checked 2026-10-19]** The Account Holder must request API access. Account Holder/Admin can manage team keys; individual API keys can be generated by eligible users, including App Manager, Customer Support, Developer, and Marketing unless disabled by an Admin. [App Store Connect API setup](https://developer.apple.com/help/app-store-connect/get-started/app-store-connect-api/).

## 4. App Store Server API and RevenueCat

- **[FACT — Apple, checked 2026-10-19]** App Store Server API supports transaction info/history, subscription status, refund history, consumption information, notification history, and test notifications. Server Notifications v2 send purchase event JWS payloads to an HTTPS server. Apple recommends v2 for new implementations. [Server API](https://developer.apple.com/documentation/appstoreserverapi), [Notifications setup](https://developer.apple.com/documentation/appstoreservernotifications/enabling-app-store-server-notifications).
- **[FACT — RevenueCat, checked 2026-10-19]** RevenueCat’s SDK handles transaction processing and subscriber state; its webhooks provide normalized events across connected stores. [RevenueCat API overview](https://www.revenuecat.com/docs/api-v2), [webhooks](https://www.revenuecat.com/docs/integrations/webhooks).
- **[INFERENCE]** With RevenueCat as the purchase layer, a separate Apple notification server is unnecessary for the basic app entitlement path. Add App Store Server API/Notifications only for a named server-side job that RevenueCat does not meet, such as a backend maintaining its own authoritative ledger or responding to Apple’s consumption-information request.
- **[UNKNOWN]** RevenueCat does not eliminate every Apple-specific server operation in all product designs. Confirm current RevenueCat support before relying on it for an edge case such as a compliance workflow or custom financial reconciliation.

## 5. Analytics, crashes, and privacy

### Options

- **[FACT — Apple, checked 2026-10-19] Native baseline:** App Store Connect Analytics and reports provide store acquisition, sales/subscription, opted-in usage, crash, and performance data. Apple thresholds data for privacy; usage analytics do not include watchOS. [Analytics overview](https://developer.apple.com/help/app-store-connect-analytics/), [analytics dashboard](https://developer.apple.com/help/app-store-connect-analytics/overview/analytics-dashboard).
- **[FACT — Apple, checked 2026-10-19] MetricKit:** current docs describe `MetricManager` daily metric reports; diagnostics arrive immediately on supported systems **[FC]**. `MXMetricManager` is marked deprecated in favor of `MetricManager` in current docs. MetricKit reports can include launch, memory, hangs, crashes, CPU, and disk-write diagnostics; reports arrive from real-world use and are not a live crash stream. New MetricManager support is described for iOS/macOS 27 and visionOS 27 diagnostics; check the selected SDK before choosing between new and legacy APIs. [MetricKit](https://developer.apple.com/documentation/metrickit), [monitoring guide](https://developer.apple.com/documentation/metrickit/monitoring-app-performance-with-metrickit).
- **[FACT — TelemetryDeck, checked 2026-10-19]** Its current pricing page advertises 50,000 events/month free for new free accounts; older free accounts may retain 100,000. The SDK sends explicit events and anonymized installation IDs/device metadata; TelemetryDeck says its SDK includes a privacy manifest and still requires the App Store privacy questionnaire. [Pricing](https://dashboard.telemetrydeck.com/plans), [privacy FAQ](https://telemetrydeck.com/docs/guides/privacy-faq/).
- **[FACT — Aptabase, checked 2026-10-19]** Aptabase advertises 20,000 events/month free, with paid plans from $10/month. It says the SDK does not send persistent device identifiers; it derives a short-lived server-side hash using IP and user agent. It lacks user-level retention/MAU metrics, and its docs say it has no public query API (the MCP wraps dashboard endpoints). [Docs and pricing](https://aptabase.com/docs), [privacy policy](https://aptabase.com/legal/privacy).
- **[FACT — PostHog, checked 2026-10-19]** PostHog advertises 1 million analytics events/month, 5,000 session recordings, 1 million feature-flag requests, and 100,000 exceptions free per month, with pay-as-you-go beyond the free allowance. It can combine analytics, replay, flags, surveys, and error tracking. [Pricing](https://posthog.com/pricing).
- **[FACT — Sentry, checked 2026-10-19]** Sentry’s Apple SDK supports iOS/iPadOS, macOS, watchOS, and visionOS. Sentry’s 2026 Developer plan is free but quota-limited. It can provide hosted crash/error aggregation and alerting; actual data capture depends on enabled SDK features and configuration. [SDK](https://github.com/getsentry/sentry-cocoa), [plan change](https://www.sentry.help/en/articles/16738709-changes-to-legacy-developer-plans-september-2026).
- **[FACT — Firebase, checked 2026-10-19]** Crashlytics supports opt-in collection configuration, and Firebase documents collected service data such as IP addresses, technical use data, and resource identifiers. Use it when the app already has a Firebase reason, not as a zero-impact default. [Crashlytics configuration](https://firebase.google.com/docs/crashlytics/ios/customize-crash-reports), [Firebase privacy](https://firebase.google.com/support/privacy).

### Privacy-label impact and recommendation

- **[FACT — Apple, checked 2026-10-19]** The app owner is responsible for App Privacy Details based on all first- and third-party data collection in the shipped app. A third-party SDK’s privacy manifest does not replace the app’s disclosure of the data collected by that SDK. [Apple data-use guidance](https://developer.apple.com/documentation/bundleresources/describing-data-use-in-privacy-manifests), [TN3184](https://developer.apple.com/documentation/technotes/tn3184-adding-data-collection-details-to-your-privacy-manifest).
- **[INFERENCE]** Lowest-data default: Apple’s built-in reporting plus local MetricKit processing, with no analytics SDK. If product usage questions become material, add TelemetryDeck or Aptabase with a small, documented event schema and no email/user IDs. Add Sentry for timely crash triage. Keep session replay off unless a specific debugging need justifies the extra capture and disclosure burden.
- **[UNKNOWN]** Exact App Privacy label categories depend on each SDK version, configuration, identifiers/events supplied, and whether data is linked to an account or used for tracking. Do not copy a generic vendor label mapping into generated apps without checking the actual SDK manifest and the actual event payloads for the selected build.

## 6. Feedback and support

- **[INFERENCE]** Default customer support should be a support URL/email in settings and store metadata, plus native mail composition where the platform supports it. Include app version and a user-written message only after showing them what will be sent. Avoid sending local productivity content or diagnostic logs by default.
- **[FACT — RevenueCat, checked 2026-10-19]** Customer Center already covers common subscription support paths and can be configured with support actions; it is the default for supported iOS targets when RevenueCat is selected. [Customer Center configuration](https://www.revenuecat.com/docs/tools/customer-center/customer-center-configuration).
- **[FACT — Apple, checked 2026-10-19]** App Store Connect API can read customer reviews and create, update, or delete developer responses. This is public review-reply management, not a private support inbox. [Review API](https://developer.apple.com/documentation/appstoreconnectapi/customer-review-responses).
- **[INFERENCE]** Treat Crisp, Intercom, or Help Scout as opt-in hosted support systems for products with sustained support volume or a real-time chat requirement. They receive customer messages and potentially user metadata, so their data-processing and privacy disclosure become part of the app’s contract.
- **[UNKNOWN]** Current total costs for Crisp, Intercom, and Help Scout depend on plan, seats, usage, and AI add-ons; I did not verify their live pricing in this pass. Native mail and Apple review replies have no separate vendor subscription fee.

## 7. Remote config and feature flags without a custom server

- **[FACT — RevenueCat, checked 2026-10-19]** Offering metadata is a remote JSON object available from RevenueCat’s SDK and can drive paywall copy/presentation and offer-related messaging without a new app release. It is tied to Offerings, so it is not a general-purpose configuration service. [Offering metadata](https://www.revenuecat.com/docs/tools/offering-metadata).
- **[FACT — Apple, checked 2026-10-19]** CloudKit’s public database is readable by all app users and does not require the user to be signed in to read. Public records count against the app container’s iCloud storage. [Public database](https://developer.apple.com/documentation/cloudkit/ckcontainer/publicclouddatabase), [CloudKit overview](https://developer.apple.com/documentation/cloudkit/ckcontainer).
- **[INFERENCE]** Use static bundled JSON for values that change only with an app update; use RevenueCat offering metadata for paywall-adjacent copy and placements; use a CloudKit public database only when creators need to update shared app configuration after release and the data is safe for every app user to read. Do not put secrets, user-specific flags, or authorization decisions in any client-readable configuration.
- **[UNKNOWN]** CloudKit public-database usage cost at a particular product’s traffic level was not modeled here. Apple quotas and capacity should be checked before using it as a high-volume remote-config backend.

## 9. Secret handling

- **[FACT — RevenueCat, checked 2026-10-19]** The RevenueCat **public app SDK key** is designed for the app binary. RevenueCat **secret REST API keys** are not: RevenueCat explicitly says to keep them out of client code and public repositories. Create v2 keys with only the needed read permissions. [API v2 authentication](https://www.revenuecat.com/docs/api-v2).
- **[FACT — Apple, checked 2026-10-19]** App Store Connect private `.p8` keys are private credentials; Apple says not to put them in client-side code or source control. Individual keys can be downloaded only once. [Creating API Keys](https://developer.apple.com/documentation/appstoreconnectapi/creating-api-keys-for-app-store-connect-api).
- **[INFERENCE]** For the owner-operated creator console, keep RevenueCat secret keys, Apple `.p8` private keys, Apple issuer/key IDs, and webhook signing secrets in macOS Keychain (or another OS-backed secret store). Read them only when making the corresponding API call; never write them into project JSON, generated apps, logs, analytics events, crash breadcrumbs, or exported reports.
- **[FACT — RevenueCat webhook docs, checked 2026-10-19]** A webhook HMAC secret is shown once when created or rotated. Store it securely and verify each signature against the raw request body. [Webhook security](https://www.revenuecat.com/docs/integrations/webhooks).
- **[INFERENCE]** Only the RevenueCat **public SDK key** belongs in the customer app binary. Do not put RevenueCat v2 secret keys, Apple `.p8` keys/JWT signing material, RevenueCat webhook credentials, or an App Store Connect API key in any app target.

# Apple guideline audit

Checked against Apple Developer guidance on 2026-09-25. This is a structural audit, not an App Review decision. Recheck linked guidance when implementing a module or preparing a specific app for release.

## Gaps found in the initial tree

| Area | Apple guidance and implication | Structural response |
| --- | --- | --- |
| Privacy declarations | Apps and included SDKs may need privacy manifests and approved reasons for covered APIs; App Store privacy answers must describe the app and third parties. [Privacy manifests](https://developer.apple.com/documentation/bundleresources/privacy-manifest-files), [privacy details](https://developer.apple.com/app-store/user-privacy-and-data-use/), [SDK requirements](https://developer.apple.com/support/third-party-SDK-requirements/) | Add `docs/privacy-security/`; make the capability contract record data and SDK use. |
| Permissions and data lifecycle | Ask for protected access when a feature needs it and provide a useful response to denial. Apps that offer account creation must allow in-app initiation of account deletion. [Privacy HIG](https://developer.apple.com/design/human-interface-guidelines/privacy), [account deletion](https://developer.apple.com/support/offering-account-deletion-in-your-app) | Add `modules/accounts/`; keep permission and recovery patterns under `ux/`. |
| Localization | Apple recommends localizable strings, plurals, device variants, and testing each supported language and region. [String catalogs](https://developer.apple.com/documentation/xcode/localizing-and-varying-text-with-a-string-catalog) | Add `docs/localization/`; include localization in each module's review. |
| Accessibility and motion | Interfaces should handle assistive technologies, readable type, contrast, and Reduce Motion. [Accessibility HIG](https://developer.apple.com/design/human-interface-guidelines/accessibility), [Motion HIG](https://developer.apple.com/design/human-interface-guidelines/motion) | Add `tests/accessibility/`; require accessible variants for every identity recipe. |
| Performance and power | Apple recommends measuring responsiveness, memory, storage, and battery use and monitoring shipped versions. [Performance and metrics](https://developer.apple.com/documentation/xcode/performance-and-metrics) | Add `docs/performance/`; include a platform and hardware verification plan. |
| App Review and distribution | Complete metadata, tested binaries, working purchases, and access for reviewers matter. Encryption use may require an export-compliance determination. [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/), [distribution](https://developer.apple.com/documentation/xcode/preparing-your-app-for-distribution), [export compliance](https://developer.apple.com/help/app-store-connect/manage-app-information/overview-of-export-compliance) | Expand the purpose of `docs/release/`; retain release work as a product-specific checklist. |
| After-release support | Apple provides TestFlight feedback, crash reports, and performance metrics for investigating shipped behavior. [Crash reports](https://developer.apple.com/documentation/xcode/acquiring-crash-reports-and-diagnostic-logs), [performance](https://developer.apple.com/documentation/xcode/improving-your-app-s-performance) | Add `docs/support/`. |
| Product value and payment | Apple's design principles start with a meaningful purpose; subscriptions require continuing value. [Design principles](https://developer.apple.com/design/human-interface-guidelines/design-principles), [subscriptions](https://developer.apple.com/app-store/subscriptions/) | Add `docs/product/`; rename the optional `subscriptions/` module to `commerce/` so one-time purchases remain possible. |
| Capability choice | Features differ by OS, hardware, permission, and entitlement. Live Activities and widgets also have different update mechanisms. [Interface fundamentals](https://developer.apple.com/documentation/technologyoverviews/interface-fundamentals), [WidgetKit strategy](https://developer.apple.com/documentation/widgetkit/developing-a-widgetkit-strategy/) | Add `config/capabilities/` and optional `modules/notifications/` and `modules/background-work/`. |
| OS and device evolution | Apple expects interfaces to adapt to new sizes and contexts, and Xcode requires platform availability checks when destinations are added. [Layout](https://developer.apple.com/design/human-interface-guidelines/layout), [multiplatform targets](https://developer.apple.com/documentation/xcode/configuring-a-multiplatform-app-target) | Add `docs/compatibility/` for release-by-release decisions. |

## Second pass: engineering gaps (2026-09-25)

The first pass covered design, privacy, and distribution. It did not cover how the code is built, tested, diagnosed, or evolved. The Sensor Atlas trial showed each gap in practice. The factory produced 51 planning files and no app target. To get a running app, the builder had to transplant another app's `project.pbxproj` with a regex script. The result compiled in Swift 5 mode, had no test target, logged sensor state with `print`, and ran its smoke test against one fixed simulator ID.

| Area | Apple guidance | Response in this factory |
| --- | --- | --- |
| First runnable build | Start from an app target that launches in Simulator; add files without editing the project by hand. [Running on devices](https://developer.apple.com/documentation/xcode/running-your-app-on-simulated-or-physical-devices) | `generate --starter ios`: an Xcode project with synchronized folders, a test target, and `make run` / `make test`. |
| Data-race safety | Swift 6 checks for data races at compile time; adoption can be incremental, but a new app has nothing to migrate. [Adopting strict concurrency in Swift 6 apps](https://developer.apple.com/documentation/swift/adoptingswift6) | Starter builds with `SWIFT_VERSION = 6.0`, approachable concurrency, and MainActor default isolation. |
| Unit tests | Swift Testing supports parameterized, parallel, async tests in Xcode 16 and later. [Swift Testing](https://developer.apple.com/documentation/testing) | Starter `AppTests/` tests the first task's state transitions. |
| Performance tests | XCTest can measure launch duration as a regression test. [XCTApplicationLaunchMetric](https://developer.apple.com/documentation/xctest/xctapplicationlaunchmetric) | Named in `PRINCIPLES.md` and the test matrix; add when a baseline exists. |
| Diagnostics | Unified logging redacts dynamic strings by default; mark values public only when they are not sensitive. [Generating log messages](https://developer.apple.com/documentation/os/generating-log-messages-from-your-code), [OSSignposter](https://developer.apple.com/documentation/os/ossignposter), [MetricKit](https://developer.apple.com/documentation/metrickit) | Starter uses `Logger`; `SECURE-FAST-DEFAULTS.md` bans `print` in shipped code. |
| Data evolution | SwiftData describes schema history with `VersionedSchema` and `SchemaMigrationPlan`. [SchemaMigrationPlan](https://developer.apple.com/documentation/swiftdata/schemamigrationplan) | `SECURE-FAST-DEFAULTS.md`: version persisted data from the first release. |
| Secrets | Store small secrets in the keychain. [Keychain services](https://developer.apple.com/documentation/security/keychain-services) | Already stated in `SECURE-FAST-DEFAULTS.md`; now linked. |
| Release is irreversible | A phased release runs 7 days (1% to 100%) and can pause for up to 30 days; you cannot roll back a release. [Phased release](https://developer.apple.com/help/app-store-connect/update-your-app/release-a-version-update-in-phases) | Release checklist: compatible data, pause plan, fix-forward path. |
| SDK and OS floor | From 2026-04-28, uploads need Xcode 26 or later with the 26 SDKs; from 2026-09-09, iOS and iPadOS uploads must target iOS 13 or later. [Upcoming requirements](https://developer.apple.com/news/upcoming-requirements/) | Release checklist and `PRINCIPLES.md` calendar row. Recheck each spring. |
| Age rating | Updated age rating questions had a 2026-01-31 deadline for uninterrupted update submission. [Upcoming requirements](https://developer.apple.com/news/upcoming-requirements/) | Release checklist. |
| Accessibility disclosure | Accessibility Nutrition Labels list nine features on the product page. They are voluntary now, and Apple says they will become required. [Overview](https://developer.apple.com/help/app-store-connect/manage-app-accessibility/overview-of-accessibility-nutrition-labels) | Release checklist: declare only features that pass Apple's evaluation criteria. |

Still deliberately open: CI choice, dependency policy, and passkeys or Sign in with Apple. Each depends on a product selecting accounts, packages, or a team setup.

## Conditional reviews for a future app

Some areas depend entirely on the eventual product: children and age ratings, health or financial data, user-generated content and moderation, managed entitlements, CarPlay eligibility, and regional distribution terms. Evaluate the relevant sections of the [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/) and the capability-specific documentation when an app selects one of these areas. For example, a CarPlay app requires a category-specific entitlement that Apple reviews. [CarPlay entitlements](https://developer.apple.com/documentation/carplay/requesting-carplay-entitlements)

## What remains deliberately open

The tree does not select a product, backend, account model, pricing, analytics vendor, deployment target, or minimum OS version. Each depends on a future app's job and chosen capabilities. The folders added here are places to record decisions; they do not make the capability mandatory.

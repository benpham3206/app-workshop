# Auto-Renewable Subscriptions on Apple Platforms: StoreKit 2 + RevenueCat (purchases-ios), Through First Renewal

Research checkpoint file. Current as of research date 2026-09-27. Status: COMPLETE (all 9 key questions plus structural proposals filled).

## 1. "Products don't load" failure modes and diagnosis

### Takeaway
Empty products/offerings is almost always an App Store Connect account/config problem, not a code bug: an inactive Paid Applications Agreement, a product not yet "Ready to Submit"/approved, a bundle ID/capability mismatch, a missing RevenueCat In-App Purchase (.p8) key, or (critically) never having submitted the IAP with the app's first version. RevenueCat surfaces most of these as configuration error code 23 and ships a dedicated troubleshooting doc (rev.cat/why-are-offerings-empty).

### Cited Findings
- FACT: RevenueCat "Configuration Error (Code 23)" means "There is an issue with your configuration... None of the products registered in the RevenueCat dashboard could be fetched from App Store Connect (or the StoreKit Configuration file if one is being used)." — [RevenueCat Community](https://community.revenuecat.com/general-questions-7/configuration-error-code-23-when-integrating-subscriptions-with-revenuecat-7529)
- FACT: Documented causes of code 23 include: App Store Connect "Paid Apps" agreement not Active (green), the In-App Purchase Configuration key not set in the RevenueCat dashboard, product IDs not matching exactly (including trailing spaces) between RevenueCat and App Store Connect, testing on Simulator instead of a real device, and products not yet in "Ready to Submit" or "Approved" state. — [RevenueCat Community](https://community.revenuecat.com/general-questions-7/ios-code-error-23-none-of-the-products-registered-in-the-revenuecat-dashboard-could-be-fetched-from-app-store-connect-3680), [rev.cat/why-are-offerings-empty (referenced)](https://community.revenuecat.com/general-questions-7/configuration-error-code-23-when-integrating-subscriptions-with-revenuecat-7529)
- FACT: On Apple Developer Forums, developers report `Product.products(for:)` returning zero results when the Paid Applications Agreement, banking, and tax information ("Business" section) are incomplete in App Store Connect — this applies even to sandbox testing, not just production — and that products typically start loading roughly 2 hours after all Business info is completed. — [Apple Developer Forums](https://developer.apple.com/forums/thread/787758)
- FACT: RevenueCat's App Store Connect Setup Guide states in a "CRITICAL" callout: when submitting a new app with subscriptions for the first time, in-app purchases **must** be included in the *same* app version submission — "They will not be reviewed otherwise" — and each subscription must show status "Ready to Submit" before it can be attached to a review. After the first approval, new IAPs can be submitted independently. — [RevenueCat: App Store Connect Setup Guide](https://www.revenuecat.com/docs/platform-resources/apple-platform-resources/app-store-connect-setup-guide)
- FACT: The same guide requires, before anything else: registering a Bundle ID with the **In-App Purchase capability enabled** in the Apple Developer Portal, then creating the matching App Store Connect app record from that Bundle ID — a bundle ID/capability mismatch is a direct cause of products failing to resolve. — [RevenueCat: App Store Connect Setup Guide](https://www.revenuecat.com/docs/platform-resources/apple-platform-resources/app-store-connect-setup-guide)
- FACT: RevenueCat requires uploading an **In-App Purchase Key** (a `.p8` key generated in App Store Connect) for RevenueCat to "securely authenticate and validate" subscription-offer requests with Apple (promotional offers, offer codes, win-back offers) and to detect consumable/non-renewing refunds; win-back offers specifically "use StoreKit 2 under the hood" so the key is required for them. Missing this key does not block basic product loading but does silently break offer eligibility, refund detection, and revenue accuracy. — [RevenueCat: iOS Subscription Offers](https://www.revenuecat.com/docs/subscription-guidance/subscription-offers/ios-subscription-offers), [RevenueCat: Handling Refunds](https://www.revenuecat.com/docs/subscription-guidance/refunds)
- FACT: Apple's own sandbox-testing documentation states "Changes you make to product metadata in App Store Connect can take up to one hour to appear in the sandbox environment," and that a Sandbox Apple Account only works for apps under the same Apple Developer Program account that created it. — [Apple: Testing In-App Purchases with Sandbox](https://developer.apple.com/documentation/storekit/testing-in-app-purchases-with-sandbox)
- FACT: A StoreKit Configuration file used in Xcode is a *local* substitute for App Store Connect data (no network, no sandbox account needed) — if a project is set to use "None" for the StoreKit configuration scheme setting, `Product.products(for:)` returns zero results even with a configuration file present in the project, per an Apple Developer Forums thread title/topic. — [Apple Developer Forums](https://developer.apple.com/forums/thread/734023)
- FACT: RevenueCat's own SDK issue tracker shows empty-offerings/empty-products reports recurring across platforms and OS versions (e.g., issues #3888, #3854, #4954, #3714 in `RevenueCat/purchases-ios`), consistent with RevenueCat's guidance that this is "most common in sandbox if something isn't hooked up right." — [GitHub: purchases-ios issues](https://github.com/RevenueCat/purchases-ios/issues)

### Inferences
- INFERENCE: Because RevenueCat's code 23 and StoreKit's empty-`Product.products(for:)` share the same root causes (agreement/banking/tax status, product review state, bundle ID/capability, sandbox propagation delay), a single first-line diagnostic checklist can serve both StoreKit-only and RevenueCat integrations.
- INFERENCE: The "must submit IAP with first app version" rule is the most consequential and least obvious failure mode for a solo developer following a "ship an empty shell first, add IAP later" instinct — this single rule likely explains a large share of "my products won't load in production" reports after an app was already approved without subscriptions.

### Gaps
- GAP: No official Apple document was found that states a precise SLA for "Paid Applications Agreement changes take effect" beyond forum anecdote (~2 hours); Apple does not publish a guaranteed propagation time.
- GAP: Did not find an Apple-published, exhaustive enumeration of code-level (non-account) causes of empty products (e.g., app-specific shared secret vs. `.p8` key confusion in the *original* StoreKit API) — this is out of scope since StoreKit 2 is the focus.

## 2. Paywall compliance

### Takeaway
Guideline 3.1.2 plus Schedule 2 §3.8(b) of the Apple Developer Program License Agreement require the subscription title, duration, price (and per-unit price where relevant), and functional Terms of Use (EULA) and Privacy Policy links to appear both in the app's purchase flow (binary) and in its App Store metadata, displayed clearly without an extra tap; a working restore mechanism and non-deceptive trial/price framing are also required. `SubscriptionStoreView` auto-generates the terms/privacy buttons and pricing display from App Store Connect data, which removes most of the manual compliance burden but must still be paired with real ToU/privacy URLs configured in App Store Connect.

### Cited Findings
- FACT: Guideline 3.1.2(a) requires that an auto-renewable subscription "must provide ongoing value to the customer, and the subscription period must last at least seven days"; 3.1.2(c) requires: "Before asking a customer to subscribe, you should clearly describe what the user will get for the price... Ensure you clearly communicate the requirements described in Schedule 2 of the Apple Developer Program License Agreement." 3.1.2(a) also warns apps "that attempt to trick users into purchasing a subscription under false pretenses or engage in bait-and-switch and scam practices... will be removed from the App Store." — [Apple App Review Guidelines §3.1.2](https://developer.apple.com/app-store/review/guidelines/)
- FACT: Apple's App Store Connect reference for "Auto-Renewable Subscription Information" requires configuring a Subscription Group Display Name and an Auto-Renewable Subscription Display Name (both localizable, shown to the user and on the system "Manage Subscriptions" page), plus the duration (1 week/1 month/2 months/3 months/6 months/1 year) and price per billing cycle; display names may not contain control characters, markup, or decorative Unicode. — [Apple: Auto-Renewable Subscription Information](https://developer.apple.com/help/app-store-connect/reference/in-app-purchases-and-subscriptions/auto-renewable-subscription-information/)
- FACT: Schedule 2 §3.8(b) practical compliance (per RevenueCat's engineering write-up) requires disclosing, both in the binary and where practical in the App Store description: "Title of auto-renewing subscription, which may be the same as the in-app product name," length of the subscription period, subscription price and per-unit pricing if applicable, and links to the Privacy Policy and Terms of Use accessible within the app. This information "must be displayed clearly and conspicuously during the purchase flow without requiring additional action from the user, such as opening a link." A commonly accepted compliance template: "A [purchase amount and period] purchase will be applied to your iTunes account [at the end of trial/intro] on confirmation. Subscriptions automatically renew unless canceled within 24-hours before the current period ends. Cancel anytime via iTunes account settings. Any unused free trial forfeits upon subscription purchase." — [RevenueCat: How to Comply with Apple's Schedule 2, Section 3.8(b)](https://www.revenuecat.com/blog/engineering/schedule-2-section-3-8-b)
- FACT: A recurring, avoidable rejection cause is a missing Terms of Use (EULA) link specifically in the **App Store description/metadata**, not just inside the app binary. — [RevenueCat: Schedule 2 §3.8(b)](https://www.revenuecat.com/blog/engineering/schedule-2-section-3-8-b)
- FACT: SwiftUI's `SubscriptionStoreView` "automatically displays buttons for the terms of service and privacy policy that you submit in App Store Connect," with `subscriptionStoreControlStyle`/modifiers to override the destination with custom URLs or a custom view; it also shows localized name/description/price per subscription option and a purchase button, orders/filters options by subscription-group rank or by the developer-provided product collection, and provides a `storeButton(_:for:)` modifier to control the automatic Close button. — [Apple: SubscriptionStoreView](https://developer.apple.com/documentation/storekit/subscriptionstoreview)
- FACT: `choosing-a-storekit-api-for-in-app-purchases` documents that only the StoreKit 2 Swift API family provides the built-in subscription store UI, refund-request sheets, subscription renewal-status info, promotional-offer/intro-offer eligibility info, and the ability to defer/suppress system Billing Issue messages — features unavailable to the original (receipt-based) API. — [Apple: Choosing a StoreKit API](https://developer.apple.com/documentation/storekit/choosing-a-storekit-api-for-in-app-purchases)
- FACT: `AppStore.sync()`'s own documentation instructs: "Include some mechanism in your app, such as a Restore Purchases button, to let users restore their Apple In-App Purchases," i.e., a restore entry point is treated by Apple as a required app affordance for any IAP-based app, independent of RevenueCat. — [Apple: AppStore.sync()](https://developer.apple.com/documentation/storekit/appstore/sync())

### Inferences
- INFERENCE: Because `SubscriptionStoreView` pulls its terms/privacy links and pricing directly from App Store Connect configuration, a paywall built with it can still fail review if the App Store Connect app metadata itself lacks a working privacy-policy URL or Terms of Use URL — the view removes UI-building work, not the underlying metadata-configuration requirement.
- INFERENCE: "Trial-vs-price prominence" and "misleading paywalls" are governed less by a single checkable rule than by the combination of 3.1.2(a)'s anti-bait-and-switch clause and the Schedule 2 §3.8(b) disclosure requirement that price/duration be visible "without requiring additional action" — a paywall that shows trial messaging in large type and true recurring price only in small print or behind a link is the most commonly cited rejection pattern in secondary sources, though Apple does not enumerate exact font-size or contrast rules.

### Gaps
- GAP: Apple's Schedule 2 of the Developer Program License Agreement is a legal document behind developer-account authentication; only secondary (RevenueCat) summaries of its §3.8(b) text were retrievable in this session, not the primary agreement text itself.
- GAP: No primary Apple source enumerating exact "trial vs. price prominence" visual requirements (e.g., minimum font size, required proximity of price to trial callout) was found; guidance here is inferred from the anti-deception language in 3.1.2(a) plus industry practice, not a specific rule.

## 3. Timeline and events (monthly + 7-day trial)

### Takeaway
For a monthly plan with a 7-day free trial: the customer is charged for the first time at the end of day 7 (trial end = first paid transaction = first billing), and the "first recurring customer" / first renewal is the second charge, roughly 30 days after that first charge (day ~37 from signup). StoreKit marks trial start with a `Transaction` whose `offer.type == .introductory` and `price == 0`; App Store Server Notifications V2 marks the trial-start purchase as `SUBSCRIBED`/`INITIAL_BUY`, the first paid renewal as `DID_RENEW` (no subtype), and only reuses `SUBSCRIBED` again if the subscription had fully lapsed and the user resubscribes (`RESUBSCRIBE`).

### Cited Findings
- FACT: Apple's full lifecycle-to-notification mapping (from the `NotificationType` documentation's "Handle use cases" tables): "Customer subscribes for the first time to any subscription within a subscription group" → `SUBSCRIBED` / `INITIAL_BUY`. "Customer resubscribes to any subscription from the same subscription group as their expired subscription" → `SUBSCRIBED` / `RESUBSCRIBE`. "The subscription successfully auto-renews" → `DID_RENEW` (no subtype). "The billing retry successfully recovers the subscription" → `DID_RENEW` / `BILLING_RECOVERY`. — [Apple: NotificationType](https://developer.apple.com/documentation/appstoreservernotifications/notificationtype)
- FACT: A trial purchase and a first paid renewal are therefore distinguishable purely from notification type/subtype: the trial-start transaction always produces `SUBSCRIBED` (with `INITIAL_BUY` or `RESUBSCRIBE`), never `DID_RENEW`; the first successful post-trial charge produces `DID_RENEW` with an empty subtype (meaning "the active subscription has successfully auto-renewed for a new transaction period"), which is the App Store Server Notifications signal for "provide the customer with access to the subscription's content or service" on renewal. — [Apple: NotificationType](https://developer.apple.com/documentation/appstoreservernotifications/notificationtype)
- FACT: Full V2 notification type/subtype vocabulary confirmed against the assignment's list: `SUBSCRIBED` (subtypes `INITIAL_BUY`, `RESUBSCRIBE`), `DID_RENEW` (subtypes none / `BILLING_RECOVERY`), `DID_FAIL_TO_RENEW` (subtypes none / `GRACE_PERIOD`), `GRACE_PERIOD_EXPIRED` (no subtype — "indicates that the billing grace period has ended without renewing the subscription, so you can turn off access"), `EXPIRED` (subtypes `VOLUNTARY`, `BILLING_RETRY`, `PRICE_INCREASE`, `PRODUCT_NOT_FOR_SALE`), `DID_CHANGE_RENEWAL_STATUS` (subtypes `AUTO_RENEW_ENABLED`, `AUTO_RENEW_DISABLED`), `REFUND` (App Store successfully refunded a transaction), plus related types `REFUND_DECLINED`, `REFUND_REVERSED`, `CONSUMPTION_REQUEST`, `PRICE_INCREASE`, `OFFER_REDEEMED`, `RENEWAL_EXTENDED`/`RENEWAL_EXTENSION`, `REVOKE` (Family Sharing loss), `DID_CHANGE_RENEWAL_PREF` (upgrade/downgrade/crossgrade). — [Apple: NotificationType](https://developer.apple.com/documentation/appstoreservernotifications/notificationtype)
- FACT: `DID_FAIL_TO_RENEW` "indicates that the subscription failed to renew due to a billing issue. The subscription enters the billing retry period. If the subtype is `GRACE_PERIOD`, continue to provide service through the grace period. If the subtype is empty, the subscription isn't in a grace period and you can stop providing the subscription service." — [Apple: NotificationType](https://developer.apple.com/documentation/appstoreservernotifications/notificationtype)
- FACT (RevenueCat side): RevenueCat's own webhook/event model mirrors this: a first purchase generates an `INITIAL_PURCHASE` event; a `RENEWAL` event corresponds to a successful auto-renewal; billing issues generate exactly one `BILLING_ISSUE` event per failure episode ("RevenueCat will only send one billing issue event — additional payment failures won't trigger additional billing issue events, unless a renewal is successful between payment failures or the subscription ends and is restarted"); once a payment method is corrected, RevenueCat "will send a renewal event" and clears `grace_period_expires_date`. — [RevenueCat: Billing Issues & Grace Periods](https://www.revenuecat.com/docs/subscription-guidance/how-grace-periods-work)
- FACT: On the StoreKit 2 client side, `Transaction.updates`/`Transaction.currentEntitlements` deliver a `VerificationResult<Transaction>` for both the trial-start and the first-renewal transaction; the code sample in Apple's docs for `Transaction.updates` explicitly branches on `transaction.revocationDate`, `transaction.expirationDate`, and `transaction.isUpgraded` to decide whether to grant/revoke access — there is no separate "is this the first renewal" flag on the client `Transaction` type itself; that distinction lives only in the *count* of transactions per `originalTransactionId`/webhook subtype, not in a dedicated field. — [Apple: Transaction.updates](https://developer.apple.com/documentation/storekit/transaction/updates-8x1nq)

### Inferences
- INFERENCE: For an app's operational definition of "first recurring customer" (i.e., first *paid, renewed* customer, as distinct from first trial start), the correct detection point is the first `DID_RENEW` (empty subtype) notification for a given `originalTransactionId` — this is unambiguous, arrives server-side, and does not depend on the app being foregrounded, unlike relying solely on `Transaction.updates`.
- INFERENCE: A 7-day trial + monthly plan produces this concrete timeline: Day 0 = trial starts, `SUBSCRIBED`/`INITIAL_BUY`, transaction price $0 (no charge). Day 7 = trial ends, first charge, still tagged as the *same* transaction lineage — StoreKit does not emit a distinct "first charge" notification separate from the original `SUBSCRIBED` event; the money moves at day 7 but the notification already fired at day 0. Day ~37 = first renewal charge, `DID_RENEW`. This means "date of first charge" and "date of `SUBSCRIBED` notification" are *not* the same when a trial is involved, which is a common source of revenue-reporting confusion.

### Gaps
- GAP: Apple's notification documentation does not explicitly state whether a distinct notification fires at the moment a trial converts to its first paid period (day 7) versus only at initial subscribe (day 0) and next renewal (day 37); based on the discussion text, no separate "trial converted" notification type exists — conversion is inferred from the JWS transaction's price/offer fields at the time of the day-37 `DID_RENEW`, not a dedicated event. This should be verified against the App Store Server API's transaction history endpoint if exact instrumentation is being built.

## 4. StoreKit 2 lifecycle

### Takeaway
The traps are all about *not missing transactions*: you must start a `Transaction.updates` listener Task before/at launch (it delivers unfinished transactions exactly once, immediately after launch — miss that window and they're gone from the listener, though still recoverable via `currentEntitlements`); you must branch on `.verified`/`.unverified` before granting access; `.pending` means wait for `Transaction.updates` rather than treating it as failure; and `AppStore.sync()` must only be called from an explicit "Restore Purchases" tap because it forces a system sign-in prompt.

### Cited Findings
- FACT: `Product.purchase()`'s result type has four cases, shown in Apple's own sample: `.success(let verificationResult)` → switch again on `.verified(let transaction)` (grant access, then `await transaction.finish()`) vs. `.unverified(let transaction, let verificationError)` ("Handle unverified transactions based on your business model"); `.pending` → "The purchase requires action from the customer. If the transaction completes, it's available through `Transaction.updates`"; `.userCancelled` → no error handling needed. — [Apple: Product.PurchaseResult](https://developer.apple.com/documentation/storekit/product/purchaseresult)
```swift
let result = try await product.purchase()
switch result {
case .success(let verificationResult):
    switch verificationResult {
    case .verified(let transaction):
        // Give the user access, then:
        await transaction.finish()
    case .unverified(let transaction, let verificationError):
        // Handle unverified transactions based on your business model.
        break
    }
case .pending:
    // Requires customer action; if it completes, it's delivered via Transaction.updates.
    break
case .userCancelled:
    break
@unknown default:
    break
}
```
— [Apple: Product.PurchaseResult](https://developer.apple.com/documentation/storekit/product/purchaseresult)
- FACT: On `Transaction.updates`: "Create a `Task` to iterate through the transactions from the listener as soon as your app launches. If your app has unfinished transactions, the `Transaction.updates` listener receives them once, immediately after the app launches. **Without the `Task` to listen for these transactions, your app may miss them.**" It also delivers transactions from Ask to Buy approvals, offer-code redemptions, App Store purchases outside the app, and purchases completed on another device — not just same-device same-session purchases (those arrive via the `purchase()` return value itself). — [Apple: Transaction.updates](https://developer.apple.com/documentation/storekit/transaction/updates-8x1nq)
```swift
final class TransactionObserver {
    var updates: Task<Void, Never>? = nil
    init() { updates = newTransactionListenerTask() }
    deinit { updates?.cancel() }
    private func newTransactionListenerTask() -> Task<Void, Never> {
        Task(priority: .background) {
            for await verificationResult in Transaction.updates {
                self.handle(updatedTransaction: verificationResult)
            }
        }
    }
    private func handle(updatedTransaction verificationResult: VerificationResult<Transaction>) {
        guard case .verified(let transaction) = verificationResult else { return } // ignore unverified
        if let revocationDate = transaction.revocationDate {
            // Remove access; transaction.revocationReason has details.
        } else if let expirationDate = transaction.expirationDate, expirationDate < Date() {
            return // expired, do nothing
        } else if transaction.isUpgraded {
            return // a higher-level transaction is active; do nothing
        } else {
            // Grant access to transaction.productID.
        }
    }
}
```
— [Apple: Transaction.updates](https://developer.apple.com/documentation/storekit/transaction/updates-8x1nq)
- FACT: `Transaction.currentEntitlements` emits "the latest transaction for each product the customer has an entitlement to," specifically: one transaction per non-consumable, the latest transaction per auto-renewable subscription whose renewal state is `subscribed` or `inGracePeriod` (implied by the discussion of state), and the latest per non-renewing subscription (including finished ones). Refunded/revoked products and *consumables* never appear here — for unfinished consumables, use `Transaction.unfinished` or `Transaction.all`. — [Apple: Transaction.currentEntitlements](https://developer.apple.com/documentation/storekit/transaction/currententitlements)
- FACT: `VerificationResult` explains that StoreKit "automatically verifies" `Transaction`, `Product.SubscriptionInfo.RenewalInfo`, and `AppTransaction` values, wrapping them as verified/unverified; for server-side re-verification, Apple recommends the App Store Server Library's `verifyAndDecodeTransaction`, `verifyAndDecodeAppTransaction`, and `verifyAndDecodeRenewalInfo` functions. It also flags a unit-mismatch trap: the JWS payloads for transactions/renewal info express price in **milliunits of currency**, while the StoreKit `Product`/`Transaction` `price` properties use ordinary currency units — "Take care not to confuse these two representations when working with both APIs." — [Apple: VerificationResult](https://developer.apple.com/documentation/storekit/verificationresult)
- FACT: `AppStore.sync()` documentation: "Include some mechanism in your app, such as a Restore Purchases button... In rare cases when a user suspects the app isn't showing all the transactions, call [sync()]... Calling [sync()] displays a system prompt that asks users to authenticate with their App Store credentials. Call this function only in response to an explicit user action, like tapping or clicking a button. In regular operations, there's no need to call [sync()]. StoreKit automatically keeps up to date transaction information... available to your app. When users reinstall your app or download it on a new device, the app automatically has all transactions available to it upon initial launch." — [Apple: AppStore.sync()](https://developer.apple.com/documentation/storekit/appstore/sync())
- FACT: `Product.PurchaseOption` covers `appAccountToken` (associates a purchase with your own user ID), promotional/win-back offer application, purchase quantity, storefront-change behavior, and introductory-offer eligibility; purchase can throw a `PurchaseError` or `StoreKitError` if an option is invalid. Testing-only options exist to simulate Ask to Buy (usable in the *sandbox*) and, with a `StoreKit configuration file` in Xcode, to simulate offer redemption and to control transaction date/renewal-rate behavior for tests. — [Apple: Product.PurchaseOption](https://developer.apple.com/documentation/storekit/product/purchaseoption)
- FACT: The original vs. StoreKit 2 API choice: StoreKit 2 (`Product`/`Transaction`) is Swift/JWS-based, available from iOS 15/macOS 12/tvOS 15/watchOS 8/visionOS 1; it is required for multi-scene visionOS apps; both APIs can coexist and see each other's transactions on iOS 15+; the original API is deprecated but still needed for pre-iOS 15 minimum deployment targets and for the Volume Purchase Program. — [Apple: Choosing a StoreKit API](https://developer.apple.com/documentation/storekit/choosing-a-storekit-api-for-in-app-purchases)

### Inferences
- INFERENCE: The safe pattern is: (1) start the `Transaction.updates` listener Task at app launch before showing any paywall UI; (2) on launch also call `Transaction.currentEntitlements` once to synchronously derive current access state (this does not require network or a sign-in prompt, unlike `AppStore.sync()`); (3) only call `AppStore.sync()` behind an explicit "Restore Purchases" button.
- INFERENCE: `appAccountToken` (a UUID you generate per logged-in user) is the mechanism that lets a server correlate a StoreKit transaction with your own account system and is what RevenueCat's SDK uses under the hood to attribute App Store Server Notifications to the correct App User ID (see §8) — omitting it, or not using a valid UUID, breaks that attribution path.

### Gaps
- GAP: Apple's `AppTransaction` documentation content was fetched but largely consists of stripped symbol references in this environment; its precise fields (e.g., `originalPlatform`, `deviceVerification`) were not independently re-confirmed beyond what's already well-established in `VerificationResult`'s discussion of `deviceVerification`/`deviceVerificationNonce`. Treat exact `AppTransaction` field names as needing a direct doc check before use in code.

## 5. Lifecycle edge cases and required app behavior

### Takeaway
Billing retry runs up to 60 days server-side; grace period (0/3/16/28 days, developer-configured) is a subset of that window during which the app must keep serving content; Family Sharing, once turned on for a product, cannot be turned back off; upgrades are immediate + prorated-refunded, downgrades/crossgrades wait for the next renewal; larger price increases need explicit customer consent or the subscription expires; and device/Apple ID changes are handled automatically by StoreKit re-delivering entitlements at launch — no app-side "restore" action should be required for the ordinary case.

### Cited Findings
- FACT: Billing Grace Period duration options are 3, 16, or 28 days, configurable to apply to all renewals or only existing-paid renewals; "If recovered within grace period: No interruption to days of paid service or revenue. If recovered after 60 days: Days of paid service reset; standard one-year rate applies [i.e., the 85%/70% revenue-share clock resets]." — [Apple: App Store Subscriptions](https://developer.apple.com/app-store/subscriptions/)
- FACT: "Apple attempts recovery for 60 days on failed renewals" and sends `DID_FAIL_TO_RENEW`; detection is available via App Store Server Notifications, StoreKit renewal state, or the App Store Server API's "Get All Subscription Statuses" endpoint. A system-provided payment-update sheet appears automatically on app launch starting iOS 16.4 when a renewal fails, and can be delayed/suppressed via StoreKit's `messages`/`display()` APIs; the developer is responsible for reinstating access if paused during recovery once the issue resolves. — [Apple: App Store Subscriptions](https://developer.apple.com/app-store/subscriptions/)
- FACT: RevenueCat: "RevenueCat will only send **one** billing issue event — additional payment failures won't trigger additional billing issue events, unless a renewal is successful between payment failures or the subscription ends and is restarted." Grace-period detection: webhook field `grace_period_expiration_at_ms` (BILLING_ISSUE events only), or `GET /subscriber`'s `grace_period_expires_date` (null when not in grace period, reset to null on a successful renewal). Amazon does not support grace periods at all. — [RevenueCat: Billing Issues & Grace Periods](https://www.revenuecat.com/docs/subscription-guidance/how-grace-periods-work)
- FACT: Family Sharing: "By default, family sharing is disabled for all new and existing in-app purchases... **Family Sharing cannot be disabled once turned on**" for a given in-app purchase — RevenueCat's docs explicitly warn "Double check that you're turning on family sharing for the correct in-app purchase!" The purchaser must still manually choose to share via device Settings; RevenueCat exposes `is_family_share` (customer history/webhooks) and `ownership_type` (REST API) to distinguish a family member's access from the purchaser's own. — [RevenueCat: Apple Family Sharing](https://www.revenuecat.com/docs/platform-resources/apple-platform-resources/apple-family-sharing)
- FACT: Apple's `REVOKE` notification "indicates that an In-App Purchase the customer was entitled to through Family Sharing is no longer available through sharing" — sent when the purchaser disables sharing, leaves the family, or gets a refund; the app also receives `paymentQueue(_:didRevokeEntitlementsForProductIdentifiers:)`. Family Sharing applies to non-consumables and auto-renewable subscriptions only. — [Apple: NotificationType](https://developer.apple.com/documentation/appstoreservernotifications/notificationtype)
- FACT: Upgrade/downgrade/crossgrade rules: "Upgrade: Immediate access, prorated refund of original subscription." "Downgrade: Continues until next renewal, then renews at lower level/price." "Crossgrade: If same duration and both pay-up-front, begins immediately; otherwise effective at next renewal. Special consideration for monthly subscriptions with 12-month commitment [new 2025 duration type]." — [Apple: App Store Subscriptions](https://developer.apple.com/app-store/subscriptions/)
- FACT: Matching notifications: an upgrade produces `DID_CHANGE_RENEWAL_PREF`/`UPGRADE` ("goes into effect immediately, starting a new billing period, and the customer receives a prorated refund"); a downgrade produces `DID_CHANGE_RENEWAL_PREF`/`DOWNGRADE` ("take effect at the next renewal date and don't affect the currently active plan"); reverting a downgrade before it takes effect produces `DID_CHANGE_RENEWAL_PREF` with an empty subtype. — [Apple: NotificationType](https://developer.apple.com/documentation/appstoreservernotifications/notificationtype)
- FACT: Price changes: "Price Decreases: Automatic renewal at lower price; no user action required." "Price Increases: Apple provides push notifications, email, and in-app messaging. Some increases require opt-in consent. Smaller, infrequent increases may result in notifications without opt-in." Developers "can preserve existing subscriber prices while increasing for new subscribers," and can delay the in-app consent sheet. If a required price-increase consent is not given, the subscription expires with `EXPIRED`/`PRICE_INCREASE`; if consent is given (or not required), `PRICE_INCREASE`/`ACCEPTED` fires; while pending, `PRICE_INCREASE`/`PENDING` fires. — [Apple: App Store Subscriptions](https://developer.apple.com/app-store/subscriptions/); [Apple: NotificationType](https://developer.apple.com/documentation/appstoreservernotifications/notificationtype)
- FACT: Refund/revocation handling on-device: the `Transaction.updates` sample checks `transaction.revocationDate` to detect a refund/revocation and remove access, using `transaction.revocationReason` for details; server-side, `REFUND` fires on a successful Apple-granted refund, `REFUND_DECLINED` if Apple declines a customer-initiated refund request, and `REFUND_REVERSED` if Apple reverses a previously granted refund after a dispute — "If your app revoked content or services as a result of the related refund, it needs to reinstate them," and "the renewal date remains unchanged when the App Store reverses a refund." — [Apple: Transaction.updates](https://developer.apple.com/documentation/storekit/transaction/updates-8x1nq); [Apple: NotificationType](https://developer.apple.com/documentation/appstoreservernotifications/notificationtype)
- FACT: New device / multiple Apple IDs / sandbox vs. production: "When users reinstall your app or download it on a new device, the app automatically has all transactions available to it upon initial launch. There's no need for users to ask your app to restore transactions — your app can immediately get the current entitlements using [`currentEntitlements`] and transaction history." A Sandbox Apple Account only works for apps under the same Apple Developer Program account that created it, and is entirely separate from a production Apple ID (no cross-environment entitlement sharing; `[Environment: Sandbox]` marks a sandbox sign-in). — [Apple: AppStore.sync()](https://developer.apple.com/documentation/storekit/appstore/sync()); [Apple: Testing In-App Purchases with Sandbox](https://developer.apple.com/documentation/storekit/testing-in-app-purchases-with-sandbox)
- FACT: RevenueCat's identity model: multiple Apple IDs/devices are reconciled through the *App User ID*, not the Apple ID — "Using an externally managed App User ID... provides a mechanism... When a user deletes and reinstalls your app — using the same App User ID will ensure they still have access... When the user logs in on multiple devices — you can honor a subscription that was purchased on one device across any other platform." Anonymous App User IDs (`$RCAnonymousID:` prefix, auto-generated when none is supplied) do **not** share subscription status across apps/platforms and are cleared on delete+reinstall. — [RevenueCat: Identifying Customers](https://www.revenuecat.com/docs/customers/identifying-customers)

### Inferences
- INFERENCE: "Day-0 auto-renew off" (a user disabling auto-renewal immediately after starting a trial, common in review/testing) maps to `DID_CHANGE_RENEWAL_STATUS`/`AUTO_RENEW_DISABLED` with no interruption of the current trial period — the app should keep granting access through the existing `expirationDate` and only revoke when `Transaction.updates`/a later `EXPIRED` notification confirms actual lapse; treating "auto-renew off" itself as a revocation event would prematurely cut off a paying (or trialing) user.
- INFERENCE: Because grace period is optional and developer-configured (not a StoreKit default), an app that does nothing beyond checking `currentEntitlements`/`expirationDate` will, by default, cut off access immediately on the *first* failed renewal unless App Store Connect's grace-period setting is turned on — this is a configuration step, not a code path, and is easy to omit.

### Gaps
- GAP: No primary Apple source was found specifying an exact numeric definition of "multiple Apple IDs" edge-case behavior (e.g., what happens if the same device signs into a second, non-sandbox Apple ID mid-subscription) beyond the general rule that entitlements follow the signed-in Apple ID's App Store account; this scenario was not directly documented and is treated as UNKNOWN pending a dedicated Apple source.

## 6. Testing

### Takeaway
Three environments cover the lifecycle: a local StoreKit configuration file/`SKTestSession` (no network, no App Store Connect setup, Xcode-signed JWS, full control including forced errors and Ask-to-Buy resolution) for early development; sandbox (real App Store Connect data, App-Store-signed JWS, accelerated but not instant renewals, default 1 month = 5 minutes, 12 renewals before auto-renew turns off) for end-to-end and server testing; and TestFlight (uses sandbox under the hood) for beta distribution. Xcode's StoreKit configuration can force errors and resolve Ask-to-Buy — sandbox cannot; sandbox can test real storefronts/price tiers and true price increases — Xcode's local config cannot.

### Cited Findings
- FACT: Three test environments compared for signing: "StoreKit Testing in Xcode" needs no App Store Connect setup and is signed by Xcode (not the App Store); "Sandbox" and "TestFlight (uses the sandbox)" both require App Store Connect setup and provide receipts/JWS transactions and subscription renewal info actually signed by the App Store. "None of the test environments charge users... The App Store doesn't send emails for purchases or refunds made in the test environments." — [Apple: Testing at All Stages of Development](https://developer.apple.com/documentation/storekit/testing-at-all-stages-of-development-with-xcode-and-the-sandbox)
- FACT: Capability matrix — Sandbox **can** but Xcode StoreKit Testing **cannot**: test different storefronts/price tiers/locale. Xcode **can** but sandbox **cannot**: introduce forced StoreKit errors; resolve (approve/reject) a deferred Ask to Buy transaction (sandbox can only *initiate* the deferred state, not resolve it); test a real price increase (sandbox marks this "No" for price-increase testing, Xcode "Yes"). Both **can**: clear purchase history; test upgrades/downgrades/crossgrades/auto-renew cancellation; reset introductory-offer eligibility; speed up/slow down renewal-period time rate; restore purchases; finish transactions; buy consumables/non-consumables; repurchase non-consumables; purchase auto-renewable and non-renewing subscriptions; redeem an offer code; refund an IAP; test an interrupted purchase; test a failed purchase (payment authorization failure); retrieve products from App Store Connect (sandbox) or optionally from a StoreKit configuration file (Xcode); manage subscriptions in-app; initiate a refund request; initiate an Ask to Buy deferred transaction; redeem intro/promotional offers; process renewal, revocation/refund, cancellation, expiration, upgrade/downgrade/crossgrade; test billing retry and billing grace period. — [Apple: Testing at All Stages of Development](https://developer.apple.com/documentation/storekit/testing-at-all-stages-of-development-with-xcode-and-the-sandbox)
- FACT: **Exact sandbox renewal-acceleration table** (App Store Connect help, "Manage Sandbox Apple Account Settings"): default speed equalization is **1 month = 5 minutes**. Options and their per-duration renewal speed / Billing Retry length / Billing Grace Period length:
  - *Renewal every 3 minutes*: 1 week→3min, 1 month→3min, 2 months→6min, 3 months→9min, 6 months→18min, 1 year→36min. Billing Retry: 6min (all). Grace Period: 3min (all).
  - *Renewal every 5 minutes (default)*: 1 week→3min, 1 month→5min, 2 months→10min, 3 months→15min, 6 months→30min, 1 year→1hr. Billing Retry: 10min (all). Grace Period: 3min (1wk) / 5min (rest).
  - *Renewal every 30 minutes*: 1 week→10min, 1 month→30min, 2 months→1hr, 3 months→1hr30min, 6 months→3hr, 1 year→6hr. Billing Retry: 1hr (all). Grace Period: 10min (1wk) / 30min (rest).
  - *Renewal every hour*: 1 week→15min, 1 month→1hr, 2 months→2hr, 3 months→3hr, 6 months→6hr, 1 year→12hr. Billing Retry: 15min (1wk) / 1hr (rest). Grace Period: 1hr (1wk) / 2hr (rest).
  "Subscriptions automatically renew up to **12 times** before auto-renewal turns off on the **thirteenth** renewal attempt." The renewal rate also controls Billing Retry and Billing Grace Period duration for that tester. — [Apple: Manage Sandbox Apple Account Settings](https://developer.apple.com/help/app-store-connect/test-in-app-purchases/manage-sandbox-apple-account-settings/)
- FACT: Sandbox setup prerequisites: an active Apple Developer Program membership; the Account Holder must have signed the Paid Applications Agreement; product info (reference name, product ID, localized name, price) set up in App Store Connect; Sandbox Apple Accounts created in App Store Connect. "A Sandbox Apple Account only works for testing Apple In-App Purchases in apps that belong to the same Apple Developer Program account you used to create it." Product-metadata changes "can take up to one hour to appear in the sandbox environment." — [Apple: Testing In-App Purchases with Sandbox](https://developer.apple.com/documentation/storekit/testing-in-app-purchases-with-sandbox)
- FACT: Interrupted-purchase testing is enabled per Sandbox Apple Account via a checkbox ("Interrupt Purchases for This Tester") in App Store Connect or iOS Sandbox Account Settings; once enabled, on-device purchase attempts by that account "will be interrupted in the sandbox environment and continue to be interrupted until the option is" disabled. — [Apple: Manage Sandbox Apple Account Settings](https://developer.apple.com/help/app-store-connect/test-in-app-purchases/manage-sandbox-apple-account-settings/)
- FACT: Clearing purchase history (per Sandbox Apple Account, in App Store Connect or on-device via Settings → Developer → [account] → Manage → Clear Purchase History) can "take longer than several minutes" for accounts with many purchases; once complete, "the transaction history is empty and the Sandbox Apple Account is eligible for introductory offers" again, and "Clearing the purchase history doesn't affect Apple In-App Purchases that customers make on the App Store" (i.e., it's sandbox-only, non-destructive to production data). — [Apple: Testing In-App Purchases with Sandbox](https://developer.apple.com/documentation/storekit/testing-in-app-purchases-with-sandbox)
- FACT: TestFlight apps "always run in the sandbox environment"; to access sandbox *controls* (renewal rate, etc.) for a TestFlight build, the tester must sign out of their production Apple Account in Media & Purchases and sign in with a Sandbox Apple Account under Settings → Developer — "Consider using a dedicated testing device when testing a TestFlight app with sandbox controls" because signing out of Media & Purchases can remove access to purchased content in production apps on that device. — [Apple: Testing In-App Purchases with Sandbox](https://developer.apple.com/documentation/storekit/testing-in-app-purchases-with-sandbox)
- FACT: RevenueCat requires minimum SDK versions to use its own "Test Store" (a store-agnostic sandbox that "automatically works with your Test Store products—no additional setup required"): iOS 5.43.0+, Android 9.9.0+, and equivalents for other platforms — distinct from Apple's own sandbox and useful for testing without any App Store Connect dependency at all. — [RevenueCat: Configuring the SDK](https://www.revenuecat.com/docs/getting-started/configuring-sdk)
- FACT: Reproducing a billing-retry failure end-to-end (RevenueCat's documented recipe): make a sandbox purchase on a real device (iOS 16.4+), background/close the app, disable renewals in Settings → App Store → Sandbox Account → Manage, wait for the accelerated renewal window to elapse so the renewal attempt fails, then relaunch the app to see the system billing-issue prompt. — [RevenueCat: Billing Issues & Grace Periods](https://www.revenuecat.com/docs/subscription-guidance/how-grace-periods-work)

### Inferences
- INFERENCE ("which test proves what"): A local StoreKit configuration file with `SKTestSession`/Transaction Manager proves *code correctness* (does the app handle verified/unverified/pending/cancelled, does it finish transactions, does it react to forced errors) without needing App Store Connect at all. Sandbox proves *configuration correctness* (do App Store Connect's actual product IDs, prices, subscription groups, offers resolve and behave under real App-Store-signed JWS) and *renewal lifecycle correctness* under accelerated time. TestFlight proves *distribution correctness* (does a signed, distributed build under real provisioning still behave, including for external testers who are not developers) — none of the three alone proves production readiness; all three together approximate it, but only a phased release / production purchase after launch proves it fully.
- INFERENCE: Because Xcode's local StoreKit configuration cannot test real price increases or real storefront/price-tier variation, and sandbox cannot resolve Ask to Buy or inject forced errors, a complete pre-launch test pass necessarily uses *both* environments — a checklist that only exercises one is incomplete by construction, not by developer oversight.

### Gaps
- GAP: Did not find a primary Apple source describing "Transaction Manager" (the Xcode debug UI for StoreKit Testing) in the same level of button-by-button detail as SKTestSession's programmatic API; content here is limited to what the "Testing at all stages" overview states about StoreKit Testing in Xcode's capabilities, not a dedicated Transaction Manager UI walkthrough.

## 7. App Store Connect configuration

### Takeaway
Subscriptions live in a subscription group (one active purchase per group per user) with a rank determining upgrade/downgrade/crossgrade behavior; durations now include weekly/monthly/annual plus a new (2025) monthly-with-12-month-commitment option; pricing spans ~800 price points per currency (100 more on request) with per-territory scheduling; intro offers are one-per-subscription-group-per-customer-lifetime, promotional offers/offer codes/win-back offers are additional retention levers (up to 10 promotional offers per subscription, offer codes now available on macOS too), and the billing grace period is a simple 3/16/28-day toggle in App Store Connect.

### Cited Findings
- FACT: "Each subscription must be assigned to a subscription group containing subscriptions with different access levels, prices, and durations. Users can only purchase one subscription per group at a time." A single group is "best practice for most apps to prevent accidental multiple purchases"; multiple groups are for apps needing simultaneous subscriptions (e.g., multiple streaming channels). Subscriptions are ranked Level 1 (most) to least service within a group, and rank determines upgrade/downgrade/crossgrade paths; multiple subscriptions can share a level if equal. — [Apple: App Store Subscriptions](https://developer.apple.com/app-store/subscriptions/)
- FACT: Durations: weekly, monthly, annual, plus a **new 2025 option**: "Monthly subscriptions with 12-month commitment (provides affordability option with commitment)." — [Apple: App Store Subscriptions](https://developer.apple.com/app-store/subscriptions/)
- FACT: Pricing: "800 price points available across all currencies and price tiers," plus "Additional 100 higher price points available upon request." Developers can set per-territory prices via the App Store Connect pricing tool (which manages exchange rates), assign tax categories, and tax treatment (inclusive/exclusive) varies by territory. Only one future price change per territory can be scheduled at a time. — [Apple: App Store Subscriptions](https://developer.apple.com/app-store/subscriptions/)
- FACT: Introductory offers: "One introductory offer per subscription group per customer," can be promoted on the App Store, and are surfaced via StoreKit APIs in-app; three discount types exist — Free Trial (no billing until offer ends), Pay as You Go (discounted recurring price for a duration), Pay Up Front (one-time price for a duration). — [Apple: App Store Subscriptions](https://developer.apple.com/app-store/subscriptions/)
- FACT: Promotional offers: developer-defined business logic/eligibility, **up to 10 offers per subscription**, same three discount types as intro offers, identified via StoreKit/App Store Server APIs plus `OfferID`/`OfferType` transaction properties; App Store Server Notifications recommended for real-time eligibility tracking. — [Apple: App Store Subscriptions](https://developer.apple.com/app-store/subscriptions/)
- FACT: Offer codes: one-time-use 18-digit codes or branded custom codes; **now available on macOS** as of the 2025 update (previously iOS/iPadOS only, requiring iOS/iPadOS 14.2+ or macOS 15+ for redemption); redeemable via redemption URL, the App Store, or in-app via the `offerCodeRedemption` method; existing subscribers can redeem a code that is an upgrade or same-level as their current plan; multiple codes across different subscription groups can be redeemed. Server Notifications should be enabled to track redemption. — [Apple: App Store Subscriptions](https://developer.apple.com/app-store/subscriptions/)
- FACT: Win-back offers (prominently featured in the 2025 update): configured with an offer priority, subscription display name/description, and an approved subscription image for App Store display; discoverable via the App Store product page/editorial placements, an automatic in-app offer sheet for eligible customers (or a custom presentation via StoreKit 2 APIs), the Apple Account's Subscription Settings, and a direct App-Store-Connect-provided URL. Example given: a $9.99-for-6-months pay-up-front win-back offer against a $39.99/year standard renewal. — [Apple: App Store Subscriptions](https://developer.apple.com/app-store/subscriptions/)
- FACT: Grace period setting: "Duration options: 3, 16, or 28 days," configurable to "Apply to all renewals (existing paid + free-to-paid transitions)" or "Apply only to existing paid renewals." — [Apple: App Store Subscriptions](https://developer.apple.com/app-store/subscriptions/)
- FACT: Revenue share: 70% in the subscription's first year of paid service, 85% after one year of continuous paid service (both minus taxes), reset if a subscription lapses more than 60 days; the Small Business Program pays 85% at every billing cycle regardless of subscription age, on all Apple platforms. — [Apple: App Store Subscriptions](https://developer.apple.com/app-store/subscriptions/)
- FACT: Practical App Store Connect setup order (RevenueCat's first-time-developer walkthrough, itself citing Apple's own flow): (1) sign the Paid Applications Agreement, set up banking, complete tax forms in Agreements/Tax/Banking; (2) register a Bundle ID with In-App Purchase capability enabled, then create the App Store Connect app record from it; (3) create a subscription group, add subscription products with pricing, configure levels; (4) create sandbox testers and test all flows; (5) upload a build from Xcode and — critically — attach the in-app purchases to that *same first submission* before submitting for review; (6) optionally apply for the Small Business Program. — [RevenueCat: App Store Connect Setup Guide](https://www.revenuecat.com/docs/platform-resources/apple-platform-resources/app-store-connect-setup-guide)

### Inferences
- INFERENCE: The new monthly-with-12-month-commitment duration and the macOS expansion of offer codes are both 2025 changes that a template built before 2025 would not account for — any generated commerce module or checklist referencing "durations" or "offer codes" should be checked against this 2025 baseline rather than older cached knowledge.
- INFERENCE: Because up to 10 promotional offers can exist per subscription and one introductory offer per subscription group, a solo developer's paywall logic needs to explicitly track "has this customer ever redeemed the intro offer for this group" (StoreKit surfaces eligibility directly) separately from promotional-offer eligibility (which is entirely developer-defined business logic, not automatically enforced by Apple beyond the 10-offer cap).

### Gaps
- GAP: Exact UI navigation paths inside the current (2026) App Store Connect web UI for each of these settings (subscription groups, grace period toggle, win-back offer configuration) were not independently verified via screenshots/live UI in this session — only documented behavior and rules were confirmed, not click-path specifics, since App Store Connect requires an authenticated developer account.

- FACT: Sandbox/webhooks/dashboard-native diagnosis path for empty offerings specifically flags: no products registered against the Offering in the RevenueCat dashboard (fix documented at `rev.cat/how-to-configure-offerings`), or none of the registered products could be fetched from App Store Connect/StoreKit configuration file (`rev.cat/why-are-offerings-empty`) — consistent with §1 above and recurring across GitHub issues (`purchases-ios` #3888, #3854, #4954, #3714). — [RevenueCat Community, GitHub issues](https://community.revenuecat.com/general-questions-7/ios-code-error-23-none-of-the-products-registered-in-the-revenuecat-dashboard-could-be-fetched-from-app-store-connect-3680)

## 9. Decision guide: StoreKit 2 alone vs RevenueCat

### Takeaway
StoreKit 2 alone is sufficient for a solo developer shipping one subscription group on Apple platforms only, with no cross-platform (Android/web) plans, no need for a remote paywall/experimentation tool, and comfort writing/maintaining their own entitlement cache and (optionally) App Store Server Notifications handling. RevenueCat earns its dependency the moment any of these hold: the product exists or will exist on Android/web and needs one subscription status across stores; the developer wants dashboard-level metrics, webhooks, or Customer Center/Paywalls without building them; or the developer wants offer/refund/family-sharing edge cases (which are numerous, per §5) handled by a maintained abstraction rather than hand-rolled JWS/notification parsing. Given RevenueCat's free tier up to $2,500 MTR, the practical cost of adopting it pre-revenue is near zero; the real trade-off is integration surface and a vendor dependency, not price.

### Cited Findings
- FACT: Apple's own "Choosing a StoreKit API" framing establishes that StoreKit 2 alone already provides everything needed for a pure-Apple, single-platform app: the built-in `SubscriptionStoreView` UI, refund-request sheets, renewal-status/auto-renew info, promotional/intro-offer eligibility, deferred Billing Issue messaging, and JWS transactions — i.e., Apple did not design StoreKit 2 as "the low-level option that needs a wrapper," it is a complete client-side subscription toolkit for Apple platforms. — [Apple: Choosing a StoreKit API](https://developer.apple.com/documentation/storekit/choosing-a-storekit-api-for-in-app-purchases)
- FACT: RevenueCat's own README frames its value-add as: server-side receipt validation, webhooks, cross-store subscription status ("know whether a user is subscribed whether they're on iOS, Android or web"), automatic MRR/conversion/churn analytics, and "over a dozen integrations" — i.e., its differentiators are backend/analytics/cross-platform, not the client purchase call itself, which StoreKit 2 already does well. — [GitHub: RevenueCat/purchases-ios README](https://github.com/RevenueCat/purchases-ios/blob/main/README.md)
- FACT: RevenueCat is free up to $2,500 Monthly Tracked Revenue, then 1% of MTR before store commission/tax — a cost structure that scales with revenue rather than requiring upfront investment, and is measured pre-commission (i.e., 1% of gross tracked revenue, not of the developer's post-Apple-cut proceeds). — [RevenueCat: Billing and account settings](https://www.revenuecat.com/docs/welcome/set-up-revenuecat/account-management)
- FACT: Adopting RevenueCat is not "free" in engineering terms even though the SDK is open source and the service has a free tier: it requires uploading a `.p8` In-App Purchase Key and configuring an App Store Connect API key relationship, setting up Apple Server Notification forwarding, and maintaining product↔entitlement↔offering mappings in a second dashboard in addition to App Store Connect — each an extra place configuration can drift or fail (as catalogued in §1/§8's empty-offerings findings). — [RevenueCat: App Store Connect Setup Guide](https://www.revenuecat.com/docs/platform-resources/apple-platform-resources/app-store-connect-setup-guide); [RevenueCat: iOS Subscription Offers](https://www.revenuecat.com/docs/subscription-guidance/subscription-offers/ios-subscription-offers)
- FACT: Data portability / lock-in: RevenueCat's App User ID system, entitlements, offerings, and CustomerInfo model are RevenueCat-specific abstractions layered over (not replacing) the underlying App Store transaction data; the underlying Apple transactions/JWS remain fully queryable directly from Apple's App Store Server API independent of RevenueCat, meaning the *source of truth* for entitlement is always recoverable from Apple even if RevenueCat is removed later — but RevenueCat's own dashboard history, MTR-based billing, webhook event stream, and Customer Center configuration would need to be rebuilt or migrated (RevenueCat documents a dedicated "Migrating to RevenueCat" section for the reverse direction, implying migration *off* RevenueCat is a manual, not tooled, path). — [RevenueCat Docs index — "Migrating to RevenueCat" section](https://www.revenuecat.com/docs/llms.txt)

### Inferences
- INFERENCE: For this factory's stated scope (a solo/AI-assisted developer building an Apple-first app per `AGENTS.md`/`PRINCIPLES.md`), the decisive variables are: (1) will this ship on Android or web too (if yes, RevenueCat avoids re-deriving StoreKit-equivalent lifecycle logic for Google Play Billing separately); (2) does the developer want a remotely configurable paywall/A-B test surface without an app update (RevenueCatUI Paywalls/Experiments provide this; StoreKit 2's `SubscriptionStoreView` is still compiled into the binary and cannot be changed without a release); (3) is the developer willing to implement and operate their own App Store Server Notifications endpoint and entitlement-cache/webhook-equivalent (StoreKit 2 alone requires this for anything beyond on-device entitlement checks, e.g., a backend that needs to know subscription status).
- INFERENCE: A solo developer does **not** need any server of their own to ship a correct StoreKit-2-only subscription: `Transaction.currentEntitlements` plus a launch-time `Transaction.updates` listener is sufficient for client-only gating, and App Store Server Notifications are only necessary if a backend (not the device) needs authoritative, real-time subscription state (e.g., for server-rendered content gating, cross-device sync without RevenueCat, or churn analytics) — RevenueCat's own docs concur that its service "doesn't require server notifications from the App Store for most subscription updates" precisely because the SDK's own receipt validation already covers the common case.
- INFERENCE: Given the free tier, a reasonable rule of thumb for the decision guide is: "prototype and pre-revenue" and "single Apple-platform, single-subscription-group app with a developer comfortable hand-rolling entitlement logic" both lean StoreKit-2-only; "cross-platform," "wants a dashboard/metrics/paywall-experimentation tool without building one," or "needs promotional/win-back/offer-code business logic beyond what's trivial to hand-roll" lean RevenueCat — and because RevenueCat is free below $2,500 MTR, there is little financial reason to delay adopting it if any of the latter apply, even pre-launch.

### Gaps
- GAP: No primary source (Apple or RevenueCat) directly enumerates "when a solo developer needs a server" as a decision framework; this section's inferences synthesize from the individually-sourced facts above (StoreKit 2's client-sufficiency claims, RevenueCat's stated server-notification optionality, and the free-tier pricing) rather than quoting a document that answers the question directly. Treat the "Inferences" in this section as reasoned synthesis, not direct citation.

### 4. Deterministic `SKTestSession` scenario list (agent-runnable, no human required)

Proposed as a fixed sequence an agent can drive via Xcode's `StoreKitTest` framework (`SKTestSession`) against a checked-in `.storekit` configuration file, to prove the lifecycle end-to-end without a sandbox Apple Account or human interaction. Each scenario names the `SKTestSession` mechanism and the observable proof point; a subagent implementing this should verify current `StoreKitTest` API names against Apple's docs before coding, since specifics were not independently re-verified against the framework's Swift API surface in this pass.

1. **Fresh install, no entitlement** — new `SKTestSession`, no prior transactions. Assert `Transaction.currentEntitlements` yields nothing and the paywall is shown. *Owner: AGENT-CAN-DO. Failure mode: a stale simulator/session state leaks a prior test's transaction — always start from a freshly reset session.*
2. **Purchase with a free trial** — call `product.purchase()` for the trial-eligible product; assert `.success(.verified(transaction))`, `transaction.offer?.type == .introductory` (or equivalent trial indicator), and that `finish()` is called. *Owner: AGENT-CAN-DO. Failure mode: forgetting to await `finish()` leaves the transaction unfinished and re-delivered on next listener start, which can be mistaken for a duplicate purchase.*
3. **Accelerate time to trial conversion** — use `SKTestSession`'s time-rate/renewal acceleration (per Apple's sandbox acceleration table analog for local testing) to advance past the trial window; assert a new transaction arrives via `Transaction.updates` representing the first paid period, and that it is *not* tagged as an introductory offer. *Owner: AGENT-CAN-DO. Failure mode: not distinguishing this transaction from the original trial transaction by re-checking `offer` fields, leading to double-counting "first paid customer."*
4. **Accelerate to first renewal** — continue advancing time to trigger a second paid transaction; assert `originalTransactionId` matches the first paid transaction and this is treated as the "first renewal"/first recurring customer event. *Owner: AGENT-CAN-DO. Failure mode: relying on wall-clock date math instead of transaction count/lineage, which breaks if the test session's acceleration factor changes.*
5. **Forced renewal failure (billing retry)** — use `SKTestSession`'s forced-error injection to fail a renewal; assert the app's entitlement-check logic keeps or revokes access per the configured grace-period assumption, and that this does not crash or silently swallow the error. *Owner: AGENT-CAN-DO. Failure mode: conflating "renewal failed" with "subscription expired" — these are different states (billing retry vs. `EXPIRED`).*
6. **Refund / revoke** — use `SKTestSession`'s refund API for the active transaction; assert `Transaction.updates` delivers a transaction with `revocationDate` set and the app revokes access immediately. *Owner: AGENT-CAN-DO. Failure mode: only checking `expirationDate` and missing `revocationDate`, which under-detects refunds that occur mid-period.*
7. **Interrupted purchase** — enable `SKTestSession`'s interrupted-purchase simulation and assert the purchase call surfaces a pending/interrupted state rather than silently failing or hanging. *Owner: AGENT-CAN-DO. Failure mode: treating an interrupted purchase the same as `.userCancelled`, which mis-attributes a recoverable state as an outright cancellation.*
8. **Ask to Buy deferral and resolution** — simulate an Ask to Buy purchase via `SKTestSession` (resolvable locally, unlike real sandbox); assert `.pending` is returned initially, then approve/reject programmatically and assert the corresponding outcome arrives via `Transaction.updates`. *Owner: AGENT-CAN-DO. Failure mode: not handling the case where the deferred transaction is later rejected, leaving the UI stuck showing a pending state indefinitely.*
9. **Clear purchase history and re-run** — reset the `SKTestSession` state and re-run scenario 1–2 to prove idempotency/no leaked state between agent runs. *Owner: AGENT-CAN-DO. Failure mode: a shared/cached simulator keychain or receipt store outside the test session's control causing a false "already purchased" result.*

This sequence intentionally excludes anything requiring a real Sandbox Apple Account, real device, or human approval (e.g., real price-increase consent, real Ask-to-Buy family-member approval, real storefront/price-tier variation) — per §6's findings, those specifically require the sandbox environment or a human, and are HUMAN-ONLY / cannot be fully automated with `SKTestSession` alone. Those should remain a separate, human-in-the-loop pre-release checklist item rather than an agent-provable scenario. Sources: [Apple: Testing at All Stages of Development](https://developer.apple.com/documentation/storekit/testing-at-all-stages-of-development-with-xcode-and-the-sandbox) (capability matrix distinguishing what `SKTestSession`/Xcode StoreKit Testing can do locally vs. what requires sandbox); scenario-to-API mapping otherwise INFERENCE from the `Product`/`Transaction`/`VerificationResult` documentation in §4, not independently re-verified against the `StoreKitTest` Swift framework's exact method names in this research pass — flagged as a GAP for whoever implements this list.

# 10 — Failure modes and guards (solo dev, subscription app, AI-built)

Role: security reviewer and failure-mode analyst. This note proposes changes and implements none. Date: 2026-09-27. Status: COMPLETE. The coordinator asked for an early stop, so no more web lookups were made after the sources listed below. Any claim not checked is marked UNKNOWN or INFERENCE.

Target architecture assumed: a thin app shell (the composition root) plus one local Swift package: `Domain` ← `Clients` (PurchaseClient, StorageClient, Clock, Analytics, and others, each with a live and a test implementation) ← `Features` (SwiftUI plus one `@Observable` model each; features never import each other). `Package.swift` enforces the dependency direction.

Severity: **doomsday** (the business, the account, or user data is gone or cannot be recovered), **major** (revenue, trust, or a release is lost for days or weeks), **routine** (friction that can be fixed in hours).
Likelihood: high / medium / low over roughly the first two years, for this builder's profile (INFERENCE unless cited).

Gaps found in existing guards:
- (a) E1 matches **filenames only**. A key pasted into a `.swift`, `.json`, `.md`, `.txt`, or `.xcconfig` file passes. So does a renamed `.p8`, and so does a RevenueCat `sk_` secret.
- (b) E1 checks the index only. A key committed and later deleted stays in Git history and passes.
- (c) `ci.yml` pins `actions/checkout@v4` by tag rather than by commit SHA.
- (d) E7 has no entitlement-failure policy.
- (e) E3 grants capabilities *by convention*. Nothing ties a packet's grant to the actual key role.

## Sources used (cited as [A#] and [V#]; each was read 2026-09-27)

- [A1] App Store Connect API keys: https://developer.apple.com/help/app-store-connect/get-started/app-store-connect-api
  - Team keys are generated by the Account Holder or an Admin, with a chosen role, and apply to all apps.
  - A key's access cannot be edited after it is generated.
  - The private key is downloaded once.
  - A revoked key cannot be reinstated.
  - Individual keys inherit the user's permissions, one per user, and an Admin can disable them.

  - Uploaded, unsubmitted builds signed with a revoked certificate may be marked Invalid Binary.

## 1. Security

**1.1 A leaked App Store Connect team API key (.p8): committed, in a log, or in CI.** Severity: **doomsday** if it has the Admin role, **major** if it has App Manager. Likelihood: medium, which is elevated because agents paste and echo files.
- **Detected by:**
  - E1 catches it only if it keeps the `.p8` name.
  - Unexpected activity in App Store Connect: new builds, TestFlight groups, metadata or price edits.
  - GitHub push-protection alerts. Whether GitHub recognizes Apple `.p8` keys is UNKNOWN.
- **Guard:**
  - (1) *Account level:* agents get no team Admin key. [A1] says a team key's role is fixed at generation, so create keys per purpose. Use the lowest role that works. Store keys in the Keychain or CI secrets and never in the repo. Refer to them by profile or environment name (note 07 §7).
  - (2) *Process:* a runbook for "revoke → regenerate → update CI → audit changes". [A1] says a revoked key cannot be reinstated, so rotation always produces a new key ID.
  - (3) *Automated:* extend readiness with a content scan (gap (a)) and an opt-in history scan (gap (b)).
- **Where:** `tooling/readiness.py`, `tests/generation/test_scaffold.py`, `core/principles/SECURE-FAST-DEFAULTS.md` (privacy/security gate 2), and a new `templates/generated-app/docs/operations/INCIDENT-RUNBOOK.md`.
- **Verification:** extend the existing test. A tracked `Sources/Config.swift` that contains `-----BEGIN PRIVATE KEY-----` makes `make check` exit 2. Removing it makes the check pass. No Xcode needed.

**1.2 A leaked In-App Purchase key (.p8).** Severity: **major**. An attacker could sign promotional or win-back offer requests and call the App Store Server API as you (INFERENCE from [A2]'s uses). Likelihood: low–medium. RevenueCat requires uploading this key (note 03 §1), so a copy also lives at the vendor.
- **Detected by:** offers being redeemed that you didn't issue, or unexpected Server API traffic. This is hard to observe (INFERENCE).
- **Guard:** the same as 1.1. [A2] also requires updating every offer that uses the key after revocation. List "which offers use key X" in `modules/commerce/README.md`.
- **Where:** `modules/commerce/README.md` and the runbook.
- **Verification:** inspection that the offers-to-key mapping exists.

**1.3 A leaked RevenueCat secret key (`sk_`).** Severity: **doomsday for customer trust**. [V1] says it can delete subscribers and grant entitlements, which can mean free access for everyone or destroyed customer records. Likelihood: medium. Agents often put it into the app, confusing it with the public SDK key.
- **Detected by:** a content scan for `sk_`; the RevenueCat dashboard audit.
- **Guard:**
  - Architectural: only the *public* SDK key may appear in the app, injected in the live `PurchaseClient` in the shell. The `sk_` key exists only on a server or in the builder's password manager. Agents never receive it (packet field).
  - Automated: the readiness content pattern `\bsk_[A-Za-z0-9_]{16,}` catches it. The exact RevenueCat key length is UNKNOWN, so use a conservative minimum. This also matches Stripe `sk_live_` and `sk_test_`, which is desirable.
- **Where:** `tooling/readiness.py`, `modules/commerce/README.md`.
- **Verification:** a test fixture with a fake `sk_…` in a `.swift` file makes the check fail. An `appl_…` public key does *not* fail.

**1.4 A signing certificate or profile leaks, or is revoked by mistake.** Severity:
- **routine** for App Store distribution: a revoked distribution certificate does not affect live apps, but unsubmitted builds may be marked Invalid Binary [A3].
- **doomsday** for a *Developer ID* Mac app: if the certificate is revoked, users can no longer install [A3].

Likelihood: low.
- **Detected by:** Invalid Binary emails, or Gatekeeper failures for Mac direct distribution.
- **Guard:** use automatic, cloud-managed signing so no `.p12` exists locally (INFERENCE: this reduces the number of copies). Never export `.p12` for agents. Keep E1.
- **Where:** `core/principles/SECURE-FAST-DEFAULTS.md`.
- **Verification:** `security find-identity -v -p codesigning` on the agent machine lists no distribution identity. This is a manual inspection on the Mac.

**1.5 Apple Account takeover (the Account Holder).** Severity: **doomsday**. It exposes all apps, payouts (banking changes), and agreements. Likelihood: low, but the impact is total.
- **Detected by:** Apple sign-in notification emails, new trusted devices, changed banking.
- **Guard (account level, no code):**
  - (1) Use FIDO security keys. [A19] requires at least two and warns of permanent lockout if all are lost, so store one off-site.
  - (2) Add a recovery contact (not re-verified: UNKNOWN current flow).
  - (3) Don't use a custom domain for the Account Holder email unless the domain has auto-renew and registrar lock. INFERENCE: if the domain expires, someone else can register it and reset the password.
  - (4) Agents never get an Apple Account session, only scoped API keys (note 07 §7).
  - (5) Do day-to-day App Store Connect work as a lower-role user, not as the Account Holder. INFERENCE: this adds overhead for a solo developer; optional.
- **Where:** a new `templates/generated-app/docs/operations/ACCOUNTS.md` (account and renewal register).
- **Verification:** the register records "security keys: 2 registered, 1 off-site" with a check date. This is a human attestation, not machine-verifiable.

**1.6 A malicious or compromised SPM dependency or SDK.** Severity: **major–doomsday**. Code runs in the app with its entitlements and in build plugins and macros on the dev machine. Likelihood: low per package, but it rises with dependency count and with agents adding packages casually.
- **Detected by:** unexpected `Package.resolved` changes in a PR diff; new network domains; new privacy-manifest entries.
- **Guard:**
  1. **A dependency allowlist check.** `docs/engineering/DEPENDENCIES.md` lists each package URL, the job it serves, its privacy impact, and its pinned version. Readiness parses `Package.resolved` and fails on any package not in the list. No Xcode needed.
  2. Commit `Package.resolved`, which pins revisions (INFERENCE for git dependencies). SwiftPM TOFU fingerprints and signing apply to *registries* [V5].
  3. **Containment by architecture.** Only the `Clients` live target (or the app shell) may depend on a vendor SDK. `Domain` and `Features` have no third-party dependencies. `Package.swift` enforces this, and a check can verify it with `swift package dump-package` (needs the Swift toolchain; Command Line Tools may suffice, INFERENCE).
  4. Reject build-tool plugins and macros from unknown authors (INFERENCE).
  5. Pin GitHub Actions by commit SHA (gap (c)).
- **Where:** `tooling/readiness.py`, the new `templates/generated-app/docs/engineering/DEPENDENCIES.md`, `ci.yml`, and `docs/agents/TASK-PACKET.md` (a worker may not add dependencies; this is already covered by E3, and the check makes it mechanical).
- **Verification:** a fixture `Package.resolved` containing an unlisted package makes `make check` exit 2. For the architecture rule, a fixture package where `Features` depends on `RevenueCat` fails the check.

**1.7 Jailbroken-device entitlement tampering; receipt or JWS forgery.** Severity: **routine** for local-only premium features, **major** for features that cost you money per use (AI calls, server compute). Likelihood: medium for a popular app, low early.
- **Detected by:**
  - server logs of JWS that fail App Store Server Library verification;
  - usage from app user IDs with no matching transaction;
  - `.unverified` results in client logs.
- **Guard:**
  - *Accept* that local checks can be patched: [A8] says "a compromised app can falsify the results."
  - Client: grant only on `.verified` [A6]. Cache the *signed JWS* or the SDK's `CustomerInfo`, never a `UserDefaults` bool (INFERENCE: a bool is trivially edited).
  - Server-cost features: the server verifies the JWS with the App Store Server Library [A6] (or checks RevenueCat server-side) before spending, and optionally checks App Attest [A8].
  - Don't spend on obfuscation (INFERENCE: poor return).
- **Where:** the entitlement policy in `modules/commerce/README.md` (see 3.1).
- **Verification:** a Domain unit test: an `.unverified` snapshot yields `.denied`. Server: a forged JWS fixture is rejected. The unit test runs in `swift test` for the Domain package, without Xcode if it has no UIKit dependency (INFERENCE).

**1.8 Insecure local storage.** Severity: **major** (a privacy breach through backups or a lost device). Likelihood: medium, because agents default to `UserDefaults`.
- **Guard:**
  - `StorageClient.live` writes user data with complete file protection [A15]; the default is weaker. Secrets and tokens go in the Keychain [A16] and never in `UserDefaults`, plists, or SwiftData.
  - Grep rule in readiness: fail on `UserDefaults` near `token|password|secret|jws` in `Sources/`. This is a heuristic warning, not an error.
- **Where:** `core/principles/SECURE-FAST-DEFAULTS.md` (add the file-protection level) and the storage contract test.
- **Verification:** an on-device inspection of the file attributes (`FileManager.attributesOfItem`, `.protectionKey`) in a unit test on a device or Simulator. **Requires Xcode.**

**1.9 Untrusted input: deep links, pasteboard, files.** Severity: major for destructive links, routine otherwise. Likelihood: medium. Already covered in principle by E4 #3.
- **Gap:** a *structural* parser. `Domain.Route.parse(URL) -> Route?` is a pure function. Links can only navigate; they never delete or pay [A14]. Prefer universal links, because a scheme claimed by two apps opens one of them at random [A14]. Read the pasteboard only on explicit user action. Imported files need a size cap and a UTType check.
- **Where:** a note in `SECURE-FAST-DEFAULTS.md`, and a starter test if a starter gains links.
- **Verification:** a table test with malformed URLs, which [A14] explicitly recommends. `swift test`.

## 2. Privacy

**2.1 An SDK collects undeclared data (privacy label mismatch → rejection or removal).** Severity: **major**. Likelihood: medium–high with analytics, crash, or attribution SDKs.
- **Detected by:**
  - Xcode's archive privacy report (**requires Xcode**);
  - App Review feedback;
  - users or researchers noticing the mismatch.
- **Guard:**
  - Per [A10], the developer is liable for third-party partners' collection, and answers can be fixed at any time without a new version.
  - Per [A9], listed SDKs must ship a manifest and, for binaries, a signature.
  - The dependency register (1.6) records each SDK's data types. The release checklist item "Review … third-party SDKs" (E5) becomes a diff: the privacy report for this archive versus the last one.
- **Where:** `DEPENDENCIES.md` and `CHECKLIST.md`.
- **Verification:** the archive privacy report is attached to the release evidence. **Requires Xcode.**

**2.2 Logging personal data** (including crash breadcrumbs and analytics properties). Already covered by E4 for `Logger`.
- **Gap:** analytics and crash SDKs bypass `Logger`. Crash logs pulled into an agent's context also carry user strings (see 6.2).
- **Guard (architectural, compile-time):** the `Analytics` protocol accepts only a closed `enum AnalyticsEvent` whose associated values are non-string (enums, buckets, counts). There is no `track(_ name: String, properties: [String: Any])`.
- **Where:** a principle line in `SECURE-FAST-DEFAULTS.md`; the Clients contract.
- **Verification:** the compiler. A free-form string event doesn't type-check. Add one Domain test that enumerates all cases (`CaseIterable`) and asserts that no payload is a `String`.

**2.3 Sending personal data to a third-party AI without consent (Guideline 5.1.2(i)).** Severity: **major** (rejection, legal exposure). Likelihood: high for an AI-flavored app. [A22] says: "clearly disclose … including with third-party AI, and obtain explicit permission."
- **Guard (architectural):**
  - The `AIClient.send(_:consent:)` call requires an `AIConsent` value that only the consent screen's model can construct (a non-public initializer in `Domain`). Revoking consent makes the stored value invalid.
  - The paywall and onboarding copy name the provider.
- **Where:** `SECURE-FAST-DEFAULTS.md`, and a future `modules/ai/README.md` if one exists. Otherwise record it in the capability contract in `AGENTS.md`.
- **Verification:** the compiler (a request can't be built without consent) plus a unit test that revocation → `.consentRequired`.

**2.4 Analytics tracking that triggers ATT.** Severity: major. The app is rejected or needs an ATT prompt that users decline. Likelihood: medium.
- [A11]: an SDK that combines data across apps is tracking "even if you don't use the SDK for these purposes." Fingerprinting is prohibited.
- **Guard:** the default is first-party metrics only (MetricKit, App Store Connect analytics; note 09). Any attribution or ads SDK in `DEPENDENCIES.md` must carry an "ATT: yes/no + evidence" column.
- **Verification:** the register review, and the privacy report (**Xcode**).

**2.5 Data deletion and export requests.** Severity: major (an App Review rejection under [A12] if accounts exist; GDPR/CCPA requests). Account deletion is already covered by E5.
- **Gap:** the architecture. `StorageClient` requires `exportAll() -> URL` and `deleteAll()`. One contract test suite runs against *every* implementation (in-memory, SwiftData, CloudKit). Deletion also clears RevenueCat server-side through the secret key on a server [V1] and revokes Sign in with Apple tokens [A12]. Warn the user that Apple billing continues [A12].
- **Where:** `modules/commerce/README.md`, `templates/generated-app/docs/privacy/PLAN.md`.
- **Verification:** a contract test: seed, `deleteAll()`, then assert empty; seed, `exportAll()`, then round-trip. `swift test` for the in-memory store; the SwiftData store **requires Xcode**.

**2.6 Children's data.** Severity: **major–doomsday** (COPPA). The amended rule's compliance date was 2026-04-22, per note 08 claim 14. Likelihood: low unless the app targets kids.
- **Guard:**
  - The product brief states "not directed at children" and the age rating matches it.
  - If the app *is* directed at kids: no third-party analytics or ads, and legal review. Guideline 1.3 was not re-fetched this session, so its current text is UNKNOWN.
  - Age signals come through an `AgeClient` edge (see 7.3).
- **Where:** `CHECKLIST.md` (age rating is already there; add "directed-at-children decision recorded").
- **Verification:** inspection.

## 3. Money and commerce

**3.1 Entitlement fails open or fails closed** (StoreKit or RevenueCat outage, offline, clock tampering). Severity:
- **major**: paying users are locked out, which brings refunds, 1-star reviews, and Guideline 2.1/3.1 complaints;
- **routine**: bounded free riding.

Likelihood: **high**. Offline use and outages are certain over time.
- Facts:
  - `currentEntitlements` includes the grace period and excludes revoked products [A7]. Its offline behavior is not documented (UNKNOWN).
  - RevenueCat serves cached `CustomerInfo` offline, keeps an entitlement for up to 3 days offline [V2], and grants purchases on-device during its own outages [V3].
  - The grace period is opt-in: 3/16/28 days [A25].
- **Guard: an explicit policy in Domain.**
  - A pure function `EntitlementPolicy.decide(snapshot: EntitlementSnapshot?, lastVerifiedAt: Date?, now: Date) -> Access`.
  - `Access` has three cases: `.granted`, `.grantedStale(until:)`, and `.denied(reason:)`.
  - Rules (proposal):
    1. `.verified` and active or in grace period → granted.
    2. `.unverified` → denied, but never delete local data.
    3. Revoked or refunded → denied immediately.
    4. Provider unreachable and last verified active within **N = 3 days** (aligned with [V2]) → `grantedStale`.
    5. Beyond N → denied, with a "Reconnect to verify" message rather than a paywall.
    6. `now < lastVerifiedAt` (the clock moved backward) → treat elapsed time as `max(0, …)` and do not extend the stale window. INFERENCE: this bounds clock-tampering gains to N days.
  - **Local-value features fail soft; cost-incurring server features fail closed at the server** (1.7).
  - **Lapsed users keep read and export access to their own data.** INFERENCE: this is a trust choice, not an Apple rule.
  - Turn the grace period on deliberately in App Store Connect (note 03 already proposes this for the checklist).
- **Where:** `modules/commerce/README.md` (a new "Entitlement failure policy" section); a Domain type in the starter when commerce is selected.
- **Verification:**
  - A table-driven Swift Testing suite over `decide()` with the `Clock` injected. Cases: offline 1 day and offline 4 days, outage during purchase, unverified, revoked, clock moved backward, and grace period. Runs under `swift test` with no Xcode if Domain is pure (INFERENCE).
  - Integration with an SKTestSession: disable the network, then expire and refund. **Requires Xcode.**

**3.2 The customer perceives a double charge** (upgrade proration, Family Sharing, trial conversion, two subscription groups). Severity: routine–major (refunds, reviews). Likelihood: medium.
- **Guard:**
  - Put all tiers in **one subscription group**, so there is one active subscription per group (note 03 §7).
  - An upgrade gives a prorated refund (note 03 §5 FACT).
  - A "Manage subscription" entry point in Settings. The system API for this was not re-verified this session (UNKNOWN).
  - The paywall states the renewal date and price. `commerce-paywall-disclosure` (E8) already covers this.
- **Where:** `modules/commerce/README.md`.
- **Verification:** an SKTestSession upgrade/downgrade scenario (**Xcode**).

**3.3 Refund abuse.** Severity: routine at small scale. Likelihood: medium.
- **Guard:**
  - Revocation removes access through `revocationDate` / `currentEntitlements` [A7].
  - Optionally answer `CONSUMPTION_REQUEST` within 12 hours **with opt-in consent only** [A13]. This needs a server, so skip it until one exists.
  - Never delete user data on refund.
- **Where:** commerce README.
- **Verification:** the SKTestSession refund scenario (**Xcode**) and the Domain policy test (revoked → denied).

**3.4 A wrong price is shipped** (a price-tier typo). Severity: **major**, and a *decrease* is **irreversible for existing subscribers**. [A5]: existing subscriptions "automatically renew at the lower price … You don't have the option to preserve the higher price." Also:
- A second scheduled change silently overwrites the first [A5].
- A price increase triggers consent emails and churn risk [A5].

Likelihood: low–medium. It rises if an agent holds an App Manager+ key.
- **Guard:**
  - (1) *Account level:* pricing needs Account Holder, Admin, or App Manager [A5]. An agent key with the **Developer** role cannot change it, so pricing is impossible *by role*, not just by policy.
  - (2) *Process:* the intended prices live in a repo manifest, `docs/release/PRICING.md` (product ID, territory, price, start date, preserve flag). Pricing edits are made by the builder only, after a 24-hour cool-off, and re-read in App Store Connect before saving.
  - (3) *Automated (future):* a read-only `doctor` diff of the App Store Connect price schedule against the manifest (note 07 §8 ship harness).
- **Where:** `TASK-PACKET.md` (Accounts field guidance), `CHECKLIST.md`, and a new `templates/generated-app/docs/release/PRICING.md`.
- **Verification:** an inspection that the agent key's role in App Store Connect under Users and Access → Integrations is Developer. Later, the `doctor` diff shows zero drift.

**3.5 Subscriber migration when switching between StoreKit and RevenueCat.** Severity: major if mishandled (existing subscribers appear unentitled). Likelihood: low–medium.
- **Guard:**
  - Apple's transactions stay the source of truth, queryable without RevenueCat (note 03 §9 FACT).
  - Keep everything vendor-specific behind `PurchaseClient`. The Domain `EntitlementSnapshot` is vendor-neutral.
  - Migration test: an existing SKTestSession subscription is recognized by the new client on first launch.
  - The exact RevenueCat import steps were not re-verified (UNKNOWN).
- **Where:** commerce README.
- **Verification:** the SKTestSession test (**Xcode**).

**3.6 Web and IAP entitlements get out of sync.** Severity: major. Likelihood: medium once web checkout exists.
- **Guard:**
  - One entitlement authority keyed by *your* user ID (a RevenueCat App User ID or your server), with `appAccountToken` set to a UUID. RevenueCat sets it only when the App User ID is a valid UUID (note 03 §8 FACT).
  - A second-device restore test.
  - EU web sales carry the withdrawal-button duty from 2026-06-19 (note 08 claim 16).
- **Where:** commerce README.
- **Verification:** a two-device sandbox test (**Xcode and device**).

## 4. Platform and account

**4.1 The Developer Program membership lapses** (for example, the card expired). Severity: **major**. The app is removed from download and updates are blocked; installed apps keep working [A20]. Whether existing subscriptions keep billing and paying out during a lapse is **UNKNOWN** (note 08 claim 7). Likelihood: medium.
- **Guard:**
  - An account register with renewal date, card expiry, and reminders 30 and 7 days ahead.
  - Auto-renew on.
  - An agent can *observe* agreement or membership errors (note 07) but renewing is human-only.
- **Where:** new `templates/generated-app/docs/operations/ACCOUNTS.md`; `config/process.json` long-lead items (already proposed in note 01).
- **Verification:** inspection that the register has dates within the past 12 months.

**4.2 The account is terminated or suspended** (a single point of failure). Severity: **doomsday**. Likelihood: low.
- Facts:
  - The Account Holder role in an *individual* membership cannot be transferred except when a minor reaches majority or the holder dies [A17].
  - Apps can be transferred to another account; reviews are retained, and subscriptions need a shared secret [A18]. Whether subscribers carry over seamlessly is UNKNOWN.
- **Guard:**
  - (1) Avoid termination triggers: truthful enrollment, no IP or copycat violations. 4.1(c) violations "can lead to removal from the Apple Developer Program" (note 05).
  - (2) **Keep everything reproducible outside Apple:** source on a remote Git host, design assets, the StoreKit config, and metadata text in the repo.
  - (3) User data must not live only in the developer's CloudKit container without an export path (2.5).
  - (4) Once revenue justifies it, consider organization enrollment (LLC). INFERENCE: this enables a transferable Account Holder and cleaner continuity; the cost is D-U-N-S and setup (note 01).
  - Honest limit: Apple owns the customer relationship for IAP. There is no mitigation that preserves subscribers if the account is terminated (INFERENCE).
- **Where:** `ACCOUNTS.md`, `PRINCIPLES.md` "Timeless" (portable data is already mentioned).
- **Verification:** a fresh clone on a second machine can build (see 7.4).

**4.3 Agreement, tax, or banking expires and payments are held.** Severity: major (payouts stop; paid IAP can't be submitted). E8 already covers `iap-agreement-blocked` and `paid-apps-agreement-inactive` for detection. The only new guard is the register rows for tax forms, bank account, and agreement version, plus "re-accept after membership renewal" [A21].

**4.4 A certificate, profile, or push key expires.** Severity:
- routine for App Store distribution (live apps are unaffected [A3]);
- **major for Mac direct distribution** if the Developer ID provisioning profile lapses while installed apps use CloudKit or push [A3].

Push `.p8` key expiry was not re-verified (UNKNOWN). Likelihood: medium.
- **Guard:** expiry dates go in the register; `doctor` lists signing identities with their expiry (note 07 §8).
- **Verification:** `security find-identity` output plus the App Store Connect certificates list in the register (Mac, no Xcode needed for `security`).

**4.5 The domain for the privacy policy or support URL expires.** Severity: **major**. The link breaks, a squatter controls your privacy text, and support email is lost. If the Apple Account email is on that domain, it becomes an account-takeover vector (INFERENCE). Likelihood: medium over several years.
- **Guard:** registrar auto-renew, registrar lock, and 2FA; register rows.
- **Automated:** an opt-in `make check-urls` (a network HEAD request on the support and privacy URLs in `STORE-PAGE.md`). It is kept off the default `make check` so offline checks stay deterministic.
- **Verification:** the command exits non-zero on a 404 or a DNS failure.

**4.6 The app is removed after a guideline change.** Severity: major. Likelihood: low–medium (for example the 2025 DSA trader removals; note 08 claim 9).
- **Guard:** follow the Apple Developer News feed; a quarterly compatibility review. Already in `AGENTS.md` ("Revisit … each major OS"); the gap is the *guideline* diff, which gets a line in `docs/compatibility/REVIEW.md`.
- **Verification:** a dated review entry exists.

**4.7 An OS release breaks the app.** Already covered by `PRINCIPLES.md` ("Work to the platform calendar") and `AGENTS.md`. No new guard.

**4.8 A build made with beta Xcode is used by accident.** Severity: routine. App Store Connect accepts beta-SDK builds for TestFlight only, not the App Store (note 08 claim 1), so the failure is late, not dangerous. Likelihood: **high here**, because the builder's Xcode Mac runs Xcode-beta 27 (HANDOFF). Already covered by the E5 checklist line and E8 `beta-xcode-submission-block`.
- **Gap:** an automated pre-upload check. The ship harness reads `DTXcodeBuild` from the archive's `Info.plist` and compares it with the released builds listed on developer.apple.com/news/releases. A path heuristic (`Xcode-beta.app`) is a weak fallback. Build-number suffix letters are *not* a reliable signal: the release build 27A266a also ends in a letter (note 08).
- **Verification:** **requires Xcode** (a real archive).

## 5. Release and data

**5.1 No rollback.** Already covered (E5, E6, `PRINCIPLES.md`).
- **Add:**
  - [A4]: pauses total at most 30 days, and anyone can download manually during a pause. A pause *limits* damage but does not contain it.
  - Keep a tagged release branch so a hotfix is a cherry-pick.
  - Expedited review exists, but its terms could not be read without sign-in (UNKNOWN).
  - Any remote kill switch needs a network dependency, so decide per product; not a default.

**5.2 A schema migration corrupts user data.** Severity: **doomsday** for the users affected. Likelihood: medium. `VersionedSchema` is already covered (E4 #4).
- **Gaps:**
  - (1) **Golden stores:** commit a fixture store created by each shipped schema version. A test migrates each one to the current schema and asserts the content.
  - (2) Copy the store file before migrating, and keep one backup.
  - (3) **Never `try!` or `fatalError` when initializing the container in the composition root.** On failure, show a recovery screen (export or retry) instead of crashing on every launch (INFERENCE; a common crash-on-launch cause).
- **Where:** `SECURE-FAST-DEFAULTS.md` (Build, diagnose, and evolve #4), `CHECKLIST.md`, and a readiness grep that warns on `try!` / `fatalError(` in files containing `ModelContainer`.
- **Verification:** the golden-store test (**requires Xcode** for SwiftData). The grep fixture test needs no Xcode.

**5.3 Old and new versions read the same data.** Covered (E5). **Add for sync:** CloudKit records written by vN+1 are read by vN on another device. Never repurpose a field. Add only optional fields. Old code ignores unknown fields (INFERENCE). A test decodes a vN+1 record fixture with the vN decoder.

**5.4 A release crashes on launch.** Severity: major. Likelihood: medium.
- **Guard:**
  - A CI or agent **Release-configuration launch test**: a UI test with `-configuration Release`, because DEBUG hooks differ (E4 #3).
  - A TestFlight soak.
  - Phased release is on (E5).
  - The 5.2 no-crash container init.
  - Watch Organizer or MetricKit, then pause [A4].
- **Verification:** a UI launch test in the Release configuration (**Xcode**).

**5.5 User data is lost on reinstall or device change.** Severity: major. Likelihood: medium.
- **Guard:**
  - `PLAN.md` states where each piece of data lives and whether it survives deletion or migration.
  - Never store user data in Caches or tmp.
  - Provide export (2.5).
  - Keychain persistence across reinstall was not verified (UNKNOWN), so don't rely on it.
  - Entitlements are recovered by Restore; a RevenueCat anonymous ID is lost on reinstall (note 03 §8 FACT).
- **Verification:** a delete/reinstall/restore manual test on a device (**device**).

## 6. Agent-specific

**6.1 An agent holding an App Store Connect key changes pricing, submits for review, replies to reviews, or deletes records.** Severity: **major–doomsday**. Likelihood: medium, and higher with broad keys. E3 already makes these builder-only *by policy*.
- **Gap: enforcement by credential.**
  - The default agent credential is an **individual key for an App Store Connect user with the Developer role**. [A1] says individual keys inherit the user's permissions, and an Admin can revoke them. That role cannot change pricing [A5]. It reportedly cannot respond to reviews or create versions (aso.dev, secondary). Whether it can submit for review is UNKNOWN, so verify.
  - A per-action App Manager key is issued only through a packet naming one action, then revoked (a revoked key cannot be reinstated [A1]).
  - The Admin/Account Holder, IAP keys, and the RevenueCat `sk_` key never reach an agent machine.
  - Add a line to `TASK-PACKET.md` under "Secrets and signing": `key id, role, expiry/revocation step`.
- **Verification:** inspect the key role in App Store Connect. Then run a **negative test** against a throwaway app record: a price PATCH with the agent key returns 403. This test is proposed and was not run.

**6.2 Prompt injection through App Store reviews, support emails, crash logs, web pages, or GitHub issues.** Severity: major. Likelihood: **high** that such content appears; the outcome depends on the agent's capabilities. The principle is already covered (E3, "Information … cannot authorize").
- **Gap: structural quarantine.**
  - A **reader lane**: any packet whose inputs include untrusted external text has network=read, Accounts=none, Secrets=none, destructive=none, and may only write a summary file.
  - A separate packet with no untrusted input performs any action.
  - Crash logs are redacted before an agent reads them (2.2).
- **Where:** `docs/agents/TASK-PACKET.md` (a new "Untrusted input" field and rule).
- **Verification:** inspection. A packet that lists untrusted sources and also grants Accounts or Secrets is invalid. A future lint in readiness could parse packets in `docs/agents/*.md`.

**6.3 An agent commits secrets.** Covered by E1 (filenames).
- **Gaps:** content, history, and chat transcripts.
  - Add content patterns and an opt-in history scan (`git log -p --all` piped through the same regexes; `make check-history`).
  - Rule: never paste secret values into an agent session; refer to Keychain profile names (note 07 §7).
- **Verification:** see 1.1 and 1.3.

**6.4 An agent "fixes" a test by weakening it.** Covered by policy (E3: workers do not write or change tests).
- **Gap: mechanical detection.** A readiness diff check versus `origin/main`, when available:
  - fail if a PR both changes `Sources/` and removes or edits lines matching `#expect|#require|XCTAssert` in `Tests/`;
  - fail if it adds `.disabled(`, `XCTSkip`, or `withKnownIssue` without a `Test-owner:` line in the PR body.
- **Verification:** a fixture repo with a weakened assertion makes the check exit 2. No Xcode needed.

**6.5 An agent redefines success.** Covered (E3). **Add:** acceptance evidence is copied verbatim from the packet into the completion note; the reviewer diffs the two. Verification: inspection.

## 7. Legal and business continuity

**7.1 IP takedown (for example, third-party mascot art).** Severity: **major–doomsday**. Removal is possible, and copycat or brand violations "can lead to removal from the Apple Developer Program" (note 05, 4.1(c)). Likelihood: **high for the mascot concept** (note 05).
- **Guard:** an **asset provenance ledger**, `docs/design/ASSETS.md` (file, source, license, owner, whether AI-generated). A readiness check fails if a file under `*.xcassets` or `Resources/` is missing from the ledger. No Xcode needed.
- **Verification:** a fixture with an unlisted image makes the check exit 2.

**7.2 A trademark dispute over the app name.** Severity: major. The name must change, and the **Bundle ID can't change after a build is uploaded** [A18], so a brand baked into the ID stays forever.
- **Guard:**
  - Search the USPTO before naming (note 05).
  - Keep the Bundle ID brand-neutral (for example `com.<legalname>.app1`). INFERENCE.
- **Where:** `config/process.json` naming action, `STORE-PAGE.md`.
- **Verification:** inspection.

**7.3 Age-assurance law non-compliance (Texas SB 2420).** Severity: major. Likelihood: medium. It has been in effect since 2026-06-04.
- Apple performs age assurance and consent. The developer determines "significant changes", may use the Declared Age Range API, and handles consent-revocation notifications ([A23]; note 08 claim 12). Utah and Louisiana are delayed to 2027, and California AB 1043 starts 2027-01-01.
- **Guard:**
  - An `AgeClient` edge (live: the Declared Age Range API; test: a fake).
  - A release-checklist line: "Is this release a significant change under Apple's Texas guidance?"
- **Verification:** inspection. The Declared Age Range API behavior **requires Xcode or a device**.

**7.4 Losing access to the only Mac with Xcode.** Severity: **major**. Likelihood: medium (theft, failure, OS-beta breakage). The builder's Xcode lives on one MacBook running Xcode-beta 27 (HANDOFF).
- **Guard:**
  - A second build path: GitHub macOS runner or Xcode Cloud. Quotas and costs are UNKNOWN (not checked).
  - Signing assets are recoverable from Apple (automatic signing) rather than living only on that Mac.
  - A released Xcode alongside the beta.
  - The repo is pushed remotely every day.
- **Verification:** a monthly clean-clone build on a second machine or runner produces an archive (**Xcode**).

**7.5 Bus factor of one.** Severity: doomsday for continuity. The individual Account Holder role transfers only on death, with Apple support [A17].
- **Guard:** a sealed "if I'm unavailable" note stored outside the repo: where the password manager is, the security keys, the registrar, and bank accounts. Plus `ACCOUNTS.md` (no secrets, only locations).
- **Verification:** attestation.

**7.6 A vendor changes pricing** (OneSignal's free plan drops to 1,000 MAU from 2026-09-01/10-01, a secondary source per note 09; RevenueCat is free under $2.5K MTR, per note 03). Severity: routine–major. Likelihood: high over time.
- **Guard:**
  - `Clients` protocols make swaps local.
  - `DEPENDENCIES.md` records the pricing-page URL, the date checked, the exit plan, and the "native alternative" (APNs, StoreKit 2).
- **Verification:** the register has check dates within the last quarter.

**7.7 A vendor shuts down or is acquired.** Severity: major. Same guard as 7.6. Apple transactions remain the source of truth, so RevenueCat's exit is recoverable (note 03 §9). Keep a periodic customer/entitlement export if the vendor offers one; RevenueCat export specifics are UNKNOWN.

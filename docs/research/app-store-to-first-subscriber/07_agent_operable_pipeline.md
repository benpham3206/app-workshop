## 1. StoreKit Test (SKTestSession) in automated tests, and the Xcode/CI split

### Takeaway
SKTestSession gives programmatic, fully local control over almost the entire subscription state machine (purchase, expire, refund, renewal-rate/time acceleration, interrupted purchases, simulated errors) with no network or sandbox Apple Account needed, and it is designed to run inside XCTest — but the primary sourced evidence describes it as an Xcode-integrated testing feature, and this session could not confirm whether it runs on a "bare" CI Mac with only Xcode Command Line Tools (no full Xcode.app) rather than the full IDE, which matters for the two-Mac (builder-Xcode-beta vs agent-Mac) setup described in the task.

### Cited Findings
- SKTestSession "provides the controls and environment configuration you use to test StoreKit transactions in Xcode. Using an instance of the SKTestSession type, you can purchase in-app products, manage transactions, refund and expire subscriptions, etc." — [SKTestSession | Apple Developer Documentation](https://developer.apple.com/documentation/storekittest/sktestsession)
- "SKTestSession is a new framework meant to be used in automated tests that allows for full programmatic control of the StoreKit Local environment and can be used to create very complete integration tests." Apple's API "lets you reset transaction history, advance time, and trigger renewals programmatically inside test cases — making subscription state-machine tests fully automatable without any sandbox account credentials." — [StoreKit Testing Improvements in iOS 14 | RevenueCat](https://www.revenuecat.com/blog/engineering/storekit-testing-in-xcode)
- "StoreKit Transaction Manager in the Local environment allows control of refunds, cancellations, permission to buy, interrupted/failed purchases, and other important scenarios for testing. Time Rate adjusts the speed of renewals to enable faster testing cycles." You can delete transactions to reset state, issue refunds, and subscription renewal is accelerated so tests don't wait for real monthly cycles. — [What's new in StoreKit 2 and StoreKit Testing in Xcode - WWDC23](https://developer.apple.com/videos/play/wwdc2023/10140/) (via search synthesis)
- "There are new APIs in StoreKitTest for simulating StoreKit errors in an SKTestSession. After creating your test session, you can call setSimulatedError with the error type you would like to test and the StoreKit API it should be simulated for." — [What's new in StoreKit testing - WWDC22](https://developer.apple.com/videos/play/wwdc2022/10039/)
- A local `.storekit` configuration file can be authored manually in Xcode, or created as a **synced** configuration file that pulls real Products/Subscriptions from App Store Connect: "For a configuration file synced with an app on App Store Connect, select the checkbox, specify your team and app... After creating your synced StoreKit Configuration file, you will have access to all the Products and Subscriptions from App Store Connect for testing." The synced products/subscriptions are **read-only** in Xcode — to change them you must edit App Store Connect and re-sync (click the Refresh icon). — [How to sync a StoreKit configuration file with App Store Connect](https://www.delasign.com/blog/xcode-sync-storekit-app-store-connect/); [Faster StoreKit testing by syncing in-app purchase products](https://www.avanderlee.com/xcode/storekit-testing-syncing-configuration-file/)
- For CI test execution generally (not StoreKit-specific), `xcodebuild` supports a two-phase flow usable without the Xcode IDE open: `build-for-testing` produces an `.xctestrun` file, and `test-without-building -xctestrun <file>.xctestrun -destination <destination-specifier>` runs tests headlessly from that artifact. Apple also ships a separate, much smaller "Command Line Tools" package (~3GB) versus the full Xcode IDE (~40GB) that "has the essentials to run tests solely from the command line." — [Speed up iOS CI using Test Without Building, xctestrun and Fastlane](https://medium.com/xcblog/speed-up-ios-ci-using-test-without-building-xctestrun-and-fastlane-a982b0060676) (third-party, not Apple primary)

### Inferences
- INFERENCE: Because SKTestSession is an XCTest-integrated Swift API (not a separate CLI binary) that operates on a `.storekit` configuration file compiled into the test target, running it in CI almost certainly requires `xcodebuild test`/`test-without-building` against a scheme that includes the `.storekit` file and a full **Xcode.app** install (or at minimum `xcode-select`'d to one) with a Simulator runtime — the lightweight "Command Line Tools only" package is unlikely to be sufficient because it lacks the Simulator runtimes and StoreKit test doubles that ship inside Xcode.app's platform SDKs. This directly bears on the task's two-Mac setup: the agent's Mac needs its own **full Xcode install** (any recent stable or beta build with StoreKit Testing support), separate from the human builder's Xcode-beta 27, to run SKTestSession scenarios in CI — it does not need to be the *same* Xcode installation, just one that supports the StoreKit Testing APIs used and can boot a Simulator.
- INFERENCE: Because the synced `.storekit` file is read-only and mirrors App Store Connect product/subscription IDs, it functions as an agent-checkable **parity oracle**: a "doctor" command can diff local `.storekit` product/subscription IDs against a fresh ASC-synced copy (or against IDs read via the App Store Connect API, see §2) to catch drift between code, local test config, and the live ASC configuration — this is a reproducible, scriptable check, not something requiring a human.
- INFERENCE: The full subscription lifecycle reproducible/resettable *locally* via SKTestSession, per the cited descriptions, spans: purchase, expire, force/accelerate renewal (time rate), refund, cancel, simulate interrupted/failed purchase, simulate "permission to buy" (Ask to Buy family-sharing gate), delete/clear transaction history, and inject simulated StoreKit API errors. This covers essentially every lifecycle event the task lists (buy, expire, force renewal, refund, billing retry/grace, interrupted purchase, Ask to Buy, time rate, clear transactions) as at least plausible via the Local testing environment, but this session did not fetch the actual method list (`buyProduct`, `expireSubscription`, `refundTransaction`, etc.) or confirm explicit **billing-retry/grace-period** simulation vs. just renewal-rate-driven expiry, so those specific method names/behaviors are Gaps, not confirmed facts.

### Gaps
- Exact SKTestSession method signatures (e.g., `buyProduct(productIdentifier:)`, `expireSubscription(productIdentifier:)`, `refundTransaction(identifier:)`, `disableDialogs`, `askToBuyEnabled`, `timeRate`) were not retrieved — the WebFetch to the Apple doc page returned only the page title, not body content, and the search/fetch tools hit a session rate limit before a retry could be attempted.
- Whether SKTestSession's "Local" testing environment specifically models **billing retry** and **billing grace period** (distinct states with their own transitions) as opposed to only "expire" and "refund," was not confirmed from a primary source this session.
- Whether SKTestSession (and `.storekit` config test runs) can execute on a macOS CI runner using only Xcode Command Line Tools (no full Xcode.app), or definitely requires a full Xcode.app + Simulator runtime, is UNKNOWN — flagged as INFERENCE above pending verification, not confirmed FACT.
- No source was found in this session for whether Apple documents a difference in SKTestSession behavior/availability between an agent's separate, non-beta Xcode and the human builder's Xcode-beta 27 (e.g., whether a `.storekit` file authored under a beta Xcode schema version opens correctly under a different Xcode major version) — this is a real risk for the two-Mac setup and is unresolved.

## 2. App Store Connect API (2026): coverage and notable gaps

### Takeaway
The App Store Connect API covers most of the metadata/pricing/TestFlight/review-submission surface an agent needs, and critically supports the once-manual "submit for review" step (`reviewSubmissions`) and subscription/intro-offer/price-point management — but it has at least one hard, structural gap that is not a permissions problem: **creating the initial app record (`POST /v1/apps`) is not supported at any role**, and several legal/financial gates (agreements, tax, banking) are largely human/Account-Holder-only with only partial API observability.

### Cited Findings
- **App record creation is impossible via API at any privilege level.** "The official App Store Connect REST API does not support creating a new app record at all, for any key at any role — a permanent Apple platform limitation, not a permissions gap that a more privileged key fixes... A direct call to `POST /v1/apps` returns '403 FORBIDDEN_ERROR'... 'The resource "apps" does not allow "CREATE". Allowed operations are: GET_COLLECTION, GET_INSTANCE, UPDATE' — confirmed with both an App Manager-role key and a freshly generated Admin-role key." — [GitHub Issue: Guide should state that creating the App Store Connect app record cannot be done via API, at any key role](https://github.com/andrewralon/app-template/issues/2)
- By contrast, **Bundle ID registration is a separate, working endpoint**: "you can create bundle IDs separately. Bundle ID / App ID registration is a separate endpoint (`POST /v1/bundleIds`) with no such restriction — that one works fine with a properly-scoped key (App Manager is sufficient) and no 2FA." — same source, [GitHub Issue #2](https://github.com/andrewralon/app-template/issues/2)
- **Review submission is a first-class API resource.** Endpoints exist for `POST /v1/reviewSubmissions` (create), `GET /v1/apps/{id}/reviewSubmissions` (list for an app), and "review submission items" to attach content (App Store version, version experiments, custom product page versions, in-app events) to a submission. — [Create a Review Submission](https://developer.apple.com/documentation/appstoreconnectapi/post-v1-reviewsubmissions); [Get Review Submissions for an App](https://developer.apple.com/documentation/appstoreconnectapi/get-v1-apps-_id_-reviewsubmissions); [Review submission items](https://developer.apple.com/documentation/appstoreconnectapi/review-submission-items); [Review submissions](https://developer.apple.com/documentation/appstoreconnectapi/review-submissions)
- **Subscription introductory offers are API-manageable**: `POST /v1/subscriptionIntroductoryOffers` creates an intro offer (free trial, pay-up-front, or pay-as-you-go) referencing price-point IDs; the typical flow is to fetch available price points for one territory, then fetch equivalent price points in other territories and repeat the create call per territory. — [Create an introductory offer](https://developer.apple.com/documentation/appstoreconnectapi/post-v1-subscriptionintroductoryoffers); [Subscription Introductory Offers](https://developer.apple.com/documentation/appstoreconnectapi/subscription-introductory-offers)
- **Age rating is a readable and writable API resource**: `GET /v1/appstoreversions/{id}/ageratingdeclaration`, `GET /v1/appinfos/{id}/ageratingdeclaration`, and `PATCH /v1/ageratingdeclarations/{id}` exist; "AgeRatingDeclaration is a set of content descriptors for your app that App Store Connect uses to assign an age rating." — [Read the Age Rating Declaration Information of an App Store Version](https://developer.apple.com/documentation/appstoreconnectapi/get-v1-appstoreversions-_id_-ageratingdeclaration); [AgeRatingDeclaration](https://developer.apple.com/documentation/appstoreconnectapi/ageratingdeclaration); [Modify an age rating declaration](https://developer.apple.com/documentation/appstoreconnectapi/patch-v1-ageratingdeclarations-_id_)
- **Agreement status is only indirectly observable via the API**: "There is a `/v1/agreements` endpoint in the App Store Connect API that can be used to check agreement status, though there's no dedicated endpoint specifically for agreement status. When required agreements are missing or expired, the API returns a 403 FORBIDDEN response with the error code 'FORBIDDEN.REQUIRED_AGREEMENTS_MISSING_OR_EXPIRED'." — [Is there a reliable way to check pending agreement status... via API?](https://developer.apple.com/forums/thread/819390)
- **Only the Account Holder can accept the Paid Applications Agreement**: "The Paid Applications Agreement is required to sell apps and is not yet active if it has not been signed or if required tax and banking information is incomplete. Only the Account Holder role can accept the Paid Applications Agreement; other team members, even admins, cannot sign it." The visible status transitions from "Pending user info" → "Processing" → "Active" once tax/banking info is filed. — [App Store Connect 'Pending Agreement': how to fix it](https://ptkd.com/journal/app-store-connect-pending-agreement-tax-forms); corroborated by [App Store Connect Help: View agreements status](https://developer.apple.com/help/app-store-connect/manage-agreements/view-agreements-status)
- **API roles map cleanly to least-privilege scoping**: Admin = full access including users/roles, financial data; App Manager = apps/metadata/builds/pricing/availability but *not* users/roles, beta testing, or sales/financial data; Developer = builds + metadata read/update, no app/version creation, no users/roles, no beta testing, no review responses, no sales/financial data; Finance = sales/financial reports, contracts, tax, banking. — [App Store Connect API Key Roles & Permissions Explained](https://aso.dev/app-store-connect/api-key-access-levels/); corroborated by [Role permissions - App Store Connect Help](https://developer.apple.com/help/app-store-connect/reference/account-management/role-permissions/)
- **Sandbox tester purchase-history reset is an API resource**: `POST /v2/sandboxTestersClearPurchaseHistoryRequests` clears all past auto-renewable-subscription and non-consumable purchases for selected sandbox testers ("Sandbox accounts with a high number of purchases may take longer to clear"); this is also exposed in the ASC web UI as a "Clear Purchase History" action. — [Clear purchase history for a sandbox tester](https://developer.apple.com/documentation/appstoreconnectapi/post-v2-sandboxtestersclearpurchasehistoryrequest); [Manage Sandbox Apple Account settings](https://developer.apple.com/help/app-store-connect/test-in-app-purchases/manage-sandbox-apple-account-settings/)
- **Sandbox renewal rate is configured per-account in the ASC UI** ("Subscription Renewal Rate... defaults to 1 month = 5 minutes... also determines the length of Billing Retry and Billing Grace Period for those testers. Subscriptions automatically renew up to 12 times before auto-renewal turns off on the thirteenth renewal attempt.") — [Manage Sandbox Apple Account settings](https://developer.apple.com/help/app-store-connect/test-in-app-purchases/manage-sandbox-apple-account-settings/); whether this specific renewal-rate *setting* (as opposed to clearing history) is exposed as a distinct App Store Connect API write endpoint was not confirmed this session (Gap).
- **Export compliance is handled through the app's `Info.plist` (`ITSAppUsesNonExemptEncryption`, `ITSEncryptionExportComplianceCode`), not primarily an App Store Connect API object**: "If your app uses encryption limited to that within the Apple operating system, no documentation is required... If your app uses an industry standard algorithm not provided within the Apple operating system, you upload your French encryption declaration in App Store Connect... proprietary encryption... upload your US CCATS and French encryption declaration in App Store Connect." Common exemption triggers: URLSession/HTTPS, Sign in with Apple, Apple Pay, TLS to Stripe/Firebase/Supabase/AWS. — [ITSEncryptionExportComplianceCode](https://developer.apple.com/documentation/bundleresources/information-property-list/itsencryptionexportcompliancecode); [Export compliance documentation for encryption](https://developer.apple.com/help/app-store-connect/reference/app-information/export-compliance-documentation-for-encryption/)

### Inferences
- INFERENCE: Combining the app-record and agreement findings, the ASC API's design intentionally keeps two classes of action human/Account-Holder-gated regardless of key privilege: (a) the very first "create this legal entity's app" action, and (b) accepting agreements/binding legal terms — both are structural, not scoping, gaps. An agent cannot "grow into" these via a more privileged key.

## 3. Irreducibly human steps

### Takeaway
The clearly human-gated actions cluster around legal/financial identity (Account Holder role, agreements, tax, banking, identity verification) and content-truthfulness attestations (export compliance classification intent, age-rating truthfulness, content rights) — but several of these are at least partially **observable** by an agent through API error codes or state fields, even though they cannot be **acted on** by an agent.

### Cited Findings
- Only the **Account Holder** role can accept the Paid Applications Agreement; "other team members, even admins, cannot sign it." — [App Store Connect 'Pending Agreement': how to fix it](https://ptkd.com/journal/app-store-connect-pending-agreement-tax-forms)
- Agreement-gating is machine-observable: calls that depend on an inactive agreement return `403 FORBIDDEN` with error code `FORBIDDEN.REQUIRED_AGREEMENTS_MISSING_OR_EXPIRED`, and the Paid Apps Agreement status field itself progresses "Pending user info" → "Processing" → "Active." — [Is there a reliable way to check pending agreement status... via API?](https://developer.apple.com/forums/thread/819390); [App Store Connect 'Pending Agreement'](https://ptkd.com/journal/app-store-connect-pending-agreement-tax-forms)
- App record creation is a human-only action in App Store Connect's web UI (or an interactive `fastlane produce`/`create_app_online` run) because the REST API structurally disallows `CREATE` on the `apps` resource at any role. — [GitHub Issue #2](https://github.com/andrewralon/app-template/issues/2)

### Inferences
- INFERENCE: Tax-interview completion and bank-account entry are, by strong implication of the Paid Apps Agreement workflow described above (status stuck at "Pending user info" until "tax and banking information is incomplete" is resolved), themselves gated behind forms that require a human to enter legally-binding financial/identity data (routing numbers, tax residency, W-8/W-9-equivalent attestations) — no API path around this was found, and this matches Apple's general pattern of keeping financial-identity data entry off the public API surface. This is an INFERENCE from the cited agreement-status behavior, not a directly cited tax/banking API doc.
- INFERENCE: Enrollment/identity verification in the Apple Developer Program is, by well-established design (not independently re-verified via a fresh 2026 source this session due to the rate limit), an interactive flow tied to a specific Apple Account with two-factor authentication and, for organizations, a D-U-N-S-number/legal-entity verification step — this is a Gap for a fresh 2026 citation but is consistent with every enrollment-related search result surfaced this session (all pointed to human "Configure Agreement, Tax, and Banking" walkthroughs, never an API).
- INFERENCE: "Truthfulness" attestations — age-rating content descriptors, export-compliance classification (does the app use non-exempt encryption, and if so which category), content-rights ownership, and (for EU) DSA trader status — are legally the humans'/Account Holder's representations even where the *data entry* happens through an API field (e.g., `PATCH /v1/ageratingdeclarations/{id}`). An agent can fill the field syntactically, but the attestation of truthfulness is a human governance decision about what to tell the agent to enter — this is the basis for the "one-time grant" pattern proposed in §8: a human decides and approves the *content* of an attestation once, after which an agent can mechanically keep it in sync with app functionality it did not decide.
- INFERENCE: Pricing/submission-timing decisions (which price tier, whether to release manually or via phased release, when to submit) are business decisions Apple leaves entirely to whoever holds API credentials — Apple does not gate these to the Account Holder specifically (App Manager-level keys can write App Store Version pricing/release fields per the role table in §2) — so these are not *Apple-mandated* human-only steps, but the task's own governance may still choose to keep the "decision" human while letting an agent execute the mechanical write once approved.

### Gaps
- No 2026-dated primary source was retrieved describing the current identity-verification flow for individual vs. organization enrollment (e.g., whether Apple still requires notarized documents or a live D-U-N-S lookup) — this session's searches did not reach that specific page before the rate limit.
- No source was found enumerating a complete, current list of Account-Holder-exclusive actions beyond the Paid Applications Agreement (e.g., is agreement renewal for the free Apple Developer Program Agreement itself also Account-Holder-only? Is there an Account Holder-only action for organization D-U-N-S changes?). Treat any such claim as UNKNOWN.
- Whether an agent can observe *tax/banking specifically* (as opposed to only the downstream Paid Apps Agreement status) — e.g., a distinct `/v1/taxCategories` or banking-status field — was not found; UNKNOWN whether such an endpoint exists at all.

## 4. Xcode command-line toolchain: archive, export, upload, notarize, simulate

### Takeaway
The archive → export → sign path is well-documented as CI-friendly using `xcodebuild` with an App Store Connect API key and `-allowProvisioningUpdates`; notarization has a modern, scriptable successor to `altool` in `notarytool`; and `simctl` fully supports headless, deterministic screenshot capture including status-bar normalization for App Store screenshots — all confirmed by primary or near-primary sources this session. The exact modern *upload* path (whether `xcodebuild` itself now uploads, vs. requiring a separate Transporter invocation) was only partially confirmed.

### Cited Findings
- `xcodebuild` supports App Store Connect API key authentication "for authentication with the Apple Developer website, enabling automatic signing via xcodebuild in headless environments such as build machines and continuous integration setups." — [App Store Connect API Key Setup — 2026 Guide](https://appconsul.com/guides/app-store-connect-api-key-setup/)
- "Running xcodebuild with authentication API keys only supports exporting archives, not building and archiving. To upload your binary, first archive your binary, create a plist file that configures archive exporting, gather your... API keys..., then run the `xcodebuild -exportArchive` command with `-allowProvisioningUpdates`, `-authenticationKeyPath`, `-authenticationKeyID`, and `-authenticationKeyIssuerID` options." — [Support App Store Connect API Keys with Xcode >= 13 (GitHub issue)](https://github.com/mxcl/xcodebuild/issues/71)
- "Apps uploaded to App Store Connect must be built with Xcode 26 or later and use the latest platform SDKs (iOS 26/iPadOS 26, tvOS 26, visionOS 26, watchOS 26 as applicable)" as of the 2026 compliance mandate. — [Apple Mandates Xcode 26 for App Store in 2026](https://www.seasiainfotech.com/blog/apple-mandates-xcode-26-for-app-store-submissions)
- Recommended secret handling for scripted ASC API auth: "issuer ID, key ID, and base64-encoded .p8 as environment variables (marked Secret), storing them as separate secrets: `ASC_ISSUER_ID`, `ASC_KEY_ID`, `ASC_KEY_P8_BASE64`." — [App Store Connect API Key Setup — 2026 Guide](https://appconsul.com/guides/app-store-connect-api-key-setup/)
- `notarytool` (introduced at WWDC21, shipping with Xcode 13) is the documented successor to `altool` for notarization: "provides a one-line command for submitting your software and waiting for your result." Example: `xcrun notarytool submit hello-1.0.pkg --keychain-profile "notary-scriptingosx" --wait`; status check via `xcrun notarytool info <UUID> --apple-id <email> --team-id <teamid> --password <password>`; credentials are typically stored once in the Keychain as a named "profile" and referenced thereafter, avoiding repeated plaintext secrets. — [Moving from altool to notarytool for Mac notarization](https://successfulsoftware.net/2023/04/28/moving-from-altool-to-notarytool-for-mac-notarization/); [Notarize a Command Line Tool with notarytool](https://scriptingosx.com/2021/07/notarize-a-command-line-tool-with-notarytool/)
- `simctl` supports fully headless, scriptable screenshot capture and status-bar normalization for store-ready screenshots: `xcrun simctl status_bar booted override --time "9:41" --batteryState charged --batteryLevel 100 --cellularBars 4 --wifiBars 3`, capture via `xcrun simctl io booted screenshot screenshot.png` ("captures the currently booted simulator at the device's native resolution — which is exactly what the App Store expects"), and reset via `xcrun simctl status_bar booted clear`. Caveat: "This changes only the visual status bar. It does not change the system time your code reads from `Date()`." — [How to override simulator status bar for App Store screenshots](https://dragosneagu.com/how-to-override-simulator-status-bar-for-app-store-screenshots/)
- Headless XCTest execution without the Xcode IDE open is supported via the two-phase `xcodebuild build-for-testing` (produces `.xctestrun`) then `xcodebuild test -xctestrun <file>.xctestrun -destination <destination-specifier>` (or `test-without-building`) pattern, and Apple ships a much smaller Command Line Tools-only package (~3GB) vs. the full Xcode IDE (~40GB) "with the essentials to run tests solely from the command line" — though (per §1) this was not confirmed sufficient specifically for SKTestSession/Simulator-dependent StoreKit tests. — [Speed up iOS CI using Test Without Building, xctestrun and Fastlane](https://medium.com/xcblog/speed-up-ios-ci-using-test-without-building-xctestrun-and-fastlane-a982b0060676)
- Xcode Cloud is a viable Apple-native CI alternative: "every Apple Developer Program member gets 25 free compute hours per month," configuration is via a graphical workflow editor rather than files/scripts, TestFlight integration is automatic, and it "does not require manual API key configurations" — but "Xcode Cloud lets you run custom scripts at exactly three points in the build process: after cloning the repo, before the build, and after the build — if your automation needs don't fit neatly into those three stages, you're stuck." fastlane, by contrast, gives "full control" via chainable "lanes" and "can integrate seamlessly with CI/CD platforms like Jenkins and Xcode Cloud, extending their capabilities." — [Comparing CI/CD tools for iOS](https://mpotapovdev.medium.com/comparing-ci-cd-tools-for-ios-d2949ff4c810); community "Why I Use Fastlane Instead of Xcode Cloud" and "Xcode Cloud scripts: Fastlane and Cocoapods" corroborate the three-hook-point limitation. — [Why I Use Fastlane Instead of Xcode Cloud](https://iothingsmaker.com/why-i-use-fastlane-instead-of-xcode-cloud-as-an-indie-ios-developer/); [Xcode Cloud scripts: Fastlane and Cocoapods](https://www.polpiella.dev/xcode-cloud-scripts-fastlane-and-cocoapods/)

### Inferences
- INFERENCE: Given `xcodebuild`'s API-key auth only covers `-exportArchive` (per the mxcl/xcodebuild GitHub issue finding), the *archive* step itself (`xcodebuild archive`) does not need API-key auth at all (it's a local compiler/signing operation using locally-resolved provisioning), while only provisioning-profile *refresh* during export needs `-allowProvisioningUpdates` + API key. This means an agent's minimal upload pipeline is: (1) `xcodebuild archive` (local signing identity + profiles, no network auth needed beyond Apple's cert/profile fetch), (2) `xcodebuild -exportArchive -allowProvisioningUpdates -authenticationKeyPath/-authenticationKeyID/-authenticationKeyIssuerID` (needs API key), (3) a separate upload step to App Store Connect (Transporter/`xcrun altool --upload-app` historically, or a newer `xcodebuild -exportArchive` with an "app-store-connect" export method that uploads directly — this exact 2026 mechanism was not confirmed, see Gaps).
- INFERENCE: Because notarization credentials can be stored once as a named Keychain profile and referenced by name thereafter, an agent's CI environment can be provisioned once (by a human, out of band) with a notary keychain profile, after which the agent invokes `notarytool submit --keychain-profile <name> --wait` with zero secret material passing through agent-visible environment variables or logs — a good template for the "one-time grant" pattern.
- INFERENCE: Xcode Cloud's three-hook limitation and lack of scriptability compared to `xcodebuild`/fastlane make it a poor fit as the *primary* automation surface for an agent-driven ship harness (too little control over exact command sequencing, no arbitrary subcommands like `doctor`/`store-test`), even though it removes the API-key management step. fastlane/raw `xcodebuild` remains the better base for the proposed harness in §8.

### Gaps
- The current (2026) canonical *upload* path was not conclusively pinned down this session: search results referenced `xcodebuild -exportArchive` for *export* but did not clearly confirm whether upload-to-App-Store-Connect is now a flag on `xcodebuild` itself, still requires the separate Transporter app / `xcrun altool --upload-app` (largely deprecated per community sources, not independently re-confirmed this session), or a newer dedicated tool. Mark the exact 2026 upload command as UNKNOWN pending direct confirmation from Apple's Xcode distribution documentation, which this session did not reach before the rate limit.
- `xcresult` inspection tooling (`xcresulttool`) command syntax/capabilities were not researched this session at all — full Gap.
- Whether a 2026 `notarytool`/Xcode release changed any of the above (e.g., new flags) was not checked against release notes this session.

## 5. Production/sandbox observation: Server Notifications V2, Server API, sandbox acceleration, RevenueCat

### Takeaway
Apple provides a documented, callable way for a server (and thus an agent-controlled backend) to request a synthetic "TEST" notification and poll its delivery status, which is a strong, agent-usable verification primitive for the whole notifications pipeline; RevenueCat has shipped an official MCP server in 2026 exposing its full v2 REST API to AI agents/IDEs, giving an agent-native interface to subscriber/entitlement state without hand-rolling Apple's raw APIs.

### Cited Findings
- `Request a Test Notification`: "asks App Store Server Notifications to send a test notification to your server... requests the App Store server send a notification with type TEST to the URL you configured in App Store Connect. When you call this endpoint, the response contains a `testNotificationToken` that identifies the notification that will be sent." A companion `Get Test Notification Status` endpoint "checks the status of the test App Store server notification sent to your server." — [Request a Test Notification](https://developer.apple.com/documentation/appstoreserverapi/request-a-test-notification); [Get Test Notification Status](https://developer.apple.com/documentation/appstoreserverapi/get-test-notification-status)
- Calling App Store Server API endpoints requires signed JWT requests: "the URLs need to be signed, which is a fairly complex process. Apple provides an app-store-server-library available in different languages like Python and Swift," covered in WWDC23's "Meet the App Store Server Library" session. — [Meet the App Store Server Library - WWDC23](https://developer.apple.com/videos/play/wwdc2023/10143/)
- RevenueCat shipped an official MCP server in 2026: "acts as a bridge between AI assistants (like Claude and ChatGPT) and the RevenueCat API, enabling natural language interactions with your subscription infrastructure." It "supports two authentication methods: API v2 Secret Key using a scoped key (read-only or write-enabled) with Bearer authentication," plus OAuth for supported clients (Claude, Codex, Copilot, Cursor, VS Code, etc.). One implementation notes a server "released on Mar 16, 2026 that provides RevenueCat billing API integration for subscriber management and entitlement operations." Setup: `claude mcp add --transport http revenuecat https://mcp.revenuecat.ai/mcp --header "Authorization: Bearer YOUR_API_V2_SECRET_KEY"`. — [Introducing RevenueCat MCP](https://www.revenuecat.com/blog/company/introducing-revenuecat-mcp); [RevenueCat MCP Server Setup](https://www.revenuecat.com/docs/tools/mcp/setup); [RevenueCat MCP Server: 26 Tools Your AI Assistant Already Knows How to Use](https://gist.github.com/revenuecatclaw/427dce0ad89ca7224a94b1e7b6fd975c)
- Community-built alternative MCP servers also exist and expose the *full* RevenueCat v2 REST API surface, e.g. "68 endpoints through 2 tools instead of 68 — using the code-mode pattern" and another exposing "the complete RevenueCat v2 REST API for seamless integration with AI agents and IDEs like Cursor and VS Code." — [github.com/TrialAndErrorAI/revenuecat-mcp](https://github.com/TrialAndErrorAI/revenuecat-mcp); [github.com/iamhenry/revenuecat-mcp](https://github.com/iamhenry/revenuecat-mcp)
- Sandbox renewal acceleration is confirmed and configurable per-account (see §2): default "1 month = 5 minutes," and the same rate setting also scales Billing Retry and Billing Grace Period durations for sandbox testers, with auto-renewal turning off after the 13th renewal attempt. — [Manage Sandbox Apple Account settings](https://developer.apple.com/help/app-store-connect/test-in-app-purchases/manage-sandbox-apple-account-settings/)

### Inferences
- INFERENCE: The Request-a-Test-Notification + Get-Test-Notification-Status pair is the single best "VERIFY" primitive an agent has for the entire server-notifications leg of the pipeline: an agent can (1) confirm the webhook URL registered in ASC is reachable and correctly verified/signed end-to-end, and (2) do so on demand, repeatably, without waiting for a real purchase/renewal event — this is a strong candidate for a `ship-harness webhook-check` command.
- INFERENCE: Because sandbox renewal rate is an account-level *setting* rather than a per-call parameter, an agent cannot pick a different rate per test run without a human (or a one-time script) having configured it in advance; the agent's role is to *consume* the configured rate (e.g., wait out an accelerated 5-minute "month" in a test loop) rather than to set it itself via API (whether a write API exists for this was a Gap in §2).
- INFERENCE: An official RevenueCat MCP server (as opposed to hand-built API calls) substantially lowers the bar for an agent to OBSERVE production subscription events (purchases, renewals, refunds, billing issues) and subscriber/entitlement state without needing its own signed-JWT App Store Server API client — for the "ship harness," wiring to RevenueCat's MCP (scoped to a read-only v2 secret key) is likely lower-effort and lower-risk than an agent maintaining raw Apple Server API JWT signing itself, *if* the app already uses RevenueCat. For apps not using RevenueCat, the agent must implement the App Store Server API library path directly (Swift/Python libraries exist per WWDC23).

### Gaps
- No official Apple-hosted App Store Connect MCP server was found or confirmed to exist as of 2026 in this session (only the community mentions of an "App Store Connect MCP server" surfaced tangentially, e.g., `glama.ai/mcp/servers/.../apple_update_age_rating`, which is a third-party project, not an Apple-official one) — mark existence of an *official* Apple ASC MCP server as UNKNOWN/likely-no based on available evidence, not confirmed either way.
- Exact request/response shape of "transaction history" and "subscription status" App Store Server API endpoints (e.g., `GET /inApps/v1/history/{transactionId}`, `GET /inApps/v1/subscriptions/{transactionId}`) and the refunds-lookup endpoint were not individually re-fetched this session — their existence is well-established in Apple's App Store Server API generally, but this session did not pull a fresh 2026 citation for each, so treat exact paths as Gaps pending direct doc confirmation.
- RevenueCat webhook payload schema/versioning specifics for 2026 were not researched this session.

## 6. fastlane: deliver, pilot, match, snapshot, precheck, produce

### Takeaway
fastlane's tools split cleanly along the API-key-vs-Apple-ID-session line documented in §2/§4: everything that maps to a scriptable ASC API resource (builds, TestFlight, most metadata) works with a pure API key and no 2FA; app-record creation (`produce`) is the one action that structurally cannot go through the API key path because the underlying ASC API doesn't support it, so it falls back to an interactive/Apple-ID-session flow.

## 7. Security/authority: scoping, key storage, session risk

### Takeaway
The App Store Connect role model (Admin/App Manager/Developer/Finance) maps directly onto API-key scoping, giving a clean way to grant an agent "upload builds + read TestFlight/review status" without granting pricing, submission, or financial visibility — the load-bearing security choice is using a **team API key with the App Manager (not Admin/Finance) role**, stored as CI secrets or Keychain, and never using an interactive Apple ID session (with its 2FA/session-cookie surface) for agent-driven automation.

### Cited Findings
- Role-to-capability mapping (repeated from §2 for this security-specific framing): Admin = "full access to all the resources and operations... including managing users, roles, apps, app metadata, builds, beta testing, sales, and financial data." App Manager = "management of apps, app metadata, and builds... does NOT have access to users and roles, beta testing, or sales and financial data." Developer = "managing builds and app metadata... cannot create or delete apps, create app versions, manage users and roles, access beta testing, respond to reviews, or view sales and financial data." Finance = "specifically designed for managing financial data... viewing sales and financial reports, as well as managing contracts, tax, and banking details." — [App Store Connect API Key Roles & Permissions Explained](https://aso.dev/app-store-connect/api-key-access-levels/)
- Recommended CI secret hygiene for ASC API keys: store "issuer ID, key ID, and base64-encoded .p8 as environment variables (marked Secret)," as separate named secrets. — [App Store Connect API Key Setup — 2026 Guide](https://appconsul.com/guides/app-store-connect-api-key-setup/)
- fastlane explicitly frames the API key as the CI-safe choice specifically *because* it avoids the Apple-ID-session/2FA path: "API key is the most reliable for CI because it doesn't require interactive 2FA" — the implicit risk being flagged is that Apple-ID-session automation requires storing/refreshing session cookies or app-specific passwords tied to a real human identity's account, a materially larger blast radius than a narrowly-scoped API key. — [Using App Store Connect API - fastlane docs](https://docs.fastlane.tools/app-store-connect-api/); [Keep using Fastlane with Apple's 2FA changes](https://drobinin.com/posts/keep-using-fastlane-with-apples-2fa-changes/)
- notarytool's Keychain-profile pattern is itself a security-relevant design: credentials are stored once, referenced by profile name thereafter, rather than passed in plaintext on every invocation. — [Moving from altool to notarytool for Mac notarization](https://successfulsoftware.net/2023/04/28/moving-from-altool-to-notarytool-for-mac-notarization/)

### Inferences
- INFERENCE: Given the role table, the correct least-privilege grant for an agent that must "upload builds and read status but not change pricing, submit, or see finance" (the task's own framing) does not exist as a single named ASC role exactly — **Developer** role comes closest (builds + metadata read/update, no sales/financial data) but Developer is documented as unable to "view sales and financial data" while presumably still able to read TestFlight/build-processing status (build/metadata scope); however whether Developer-role keys can read `reviewSubmissions`/App Store review status was not independently confirmed this session — likely yes (App Store Connect API keys of Developer role typically retain read access to processing/build status per general documented behavior), but flagged as INFERENCE, not FACT, since no source in this session explicitly enumerated Developer-role visibility into `reviewSubmissions`.
- INFERENCE: "Submit for review" and "change pricing" both plausibly require **App Manager** or higher (since App Manager explicitly covers "app versions... pricing, and availability" per the cited role description) — meaning a strict "can upload/read but never submit/reprice" agent grant may require a **Developer**-role key for day-to-day CI (build upload, TestFlight, status polling) plus a separate, more privileged, human-invoked or explicitly task-granted App Manager key/action for the submit/price/finance-adjacent steps — this two-tier key design is the natural security architecture implied by the role table, though it was not itself described as a named pattern in any source found this session.
- INFERENCE: An interactive Apple ID session (as opposed to an API key) is a strictly worse choice for agent automation on every axis found this session: it needs 2FA or session-cookie handling (drobinin.com), it is tied to a specific human's account rather than a scoped, revocable team key, and it has no documented role-based scoping equivalent to the API key role table — so giving an agent an Apple ID session (vs. a scoped API key) should be treated as categorically prohibited in the ship-harness design, not just discouraged.

### Gaps
- No source found this session enumerating exactly which ASC API resources a **Developer**-role key can read that overlap with `reviewSubmissions`/review status polling — this is the crux of "read status without seeing finance/pricing" and remains unconfirmed at the resource-level granularity.
- No source found on Apple's own recommended key-rotation policy or maximum key lifetime/expiry behavior for ASC API keys in 2026.
- Whether Apple has (as of 2026) introduced any more granular scoping mechanism than the four named roles (e.g., per-app key restriction, which is a known ASC feature allowing a key to be scoped to specific apps) was not explicitly re-confirmed this session, though this is INFERENCE-level general knowledge that per-app key scoping exists as an ASC feature — treat as a Gap for a fresh citation.

| App Privacy answers | Likely removable | Standard metadata-shaped ASC resource by strong inference; exact endpoint not independently re-verified this session (§2 Gaps) — reduce to one-time human content decision + agent-mechanical entry |
| Age rating declaration | Reducible to one-time grant | API can read/write the fields (`ageratingdeclarations`), but the *truthfulness* of content descriptors is a human judgment about the app's actual content — a human approves the descriptor set once per major content change, agent keeps the ASC record in sync thereafter (§3) |
| Export compliance classification | Reducible to one-time grant | Mechanically an `Info.plist` key + possible doc upload; the encryption-use *classification* is a one-time human/legal judgment per §2's cited exemption criteria, reusable across builds unless encryption usage changes |
| Build archive/export/upload | Removable | `xcodebuild`/API-key automatable end-to-end for export; exact upload command has a residual Gap but is not human-only in kind (§4) |
| TestFlight group management & distribution | Removable | Standard ASC API/`pilot` surface (§2, §6) |
| Review submission (the act of submitting) | Reducible to one-time-per-release grant | Technically API-automatable (`reviewSubmissions`), but recommended to keep as an explicit task-packet-granted action since it's a point-of-no-return business decision, not an Apple-mandated human gate (§8) |
| Pricing / phased-release decisions | Reducible to one-time-per-decision grant | Not Apple-mandated human-only (App Manager-role keys can write these fields per §2's role table); should remain a human *decision*, agent-executed *action* once approved |
| Screenshot capture | Removable | Fully `simctl`-scriptable including status-bar normalization (§4) |
| Sandbox subscription-lifecycle testing (purchase/renew/refund/expire) | Removable | SKTestSession is purpose-built for this, no sandbox Apple Account needed (§1) |
| Production subscription-event observation | Removable | App Store Server Notifications V2 self-test + App Store Server API / RevenueCat MCP for read access (§5) |
| Customer review reading/response drafting | Reducible to one-time-per-policy grant | Standard read API; response *content* judgment is a human/policy decision, posting the approved text is mechanical |

Overall pattern: the truly irreducible human core is small — identity/legal-entity enrollment, agreement/tax/banking legal execution, and the structural app-record-creation gap — while most "human steps" observed in practice are actually **content or policy decisions that only need to be made once (or once per material change)**, after which the mechanical execution is fully within an agent's reach through documented, sourced interfaces.
